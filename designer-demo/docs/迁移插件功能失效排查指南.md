# 迁移插件功能失效排查指南

> 适用场景：从 `packages/*` 迁到 `designer-demo`（或 `lowcode-kit/packages/designer`）的插件，**面板能打开、大部分功能正常，但某个按钮/联动「点了没反应」**。  
> 典型案例：Events 面板绑定事件后的 **Locate Code（`</>`）** 无法打开左侧 Page JS 并定位函数。

相关文档：

- [插件迁移指南](./PLUGIN_MIGRATION.md)（怎么迁）
- [设计器去依赖改造方案](./设计器去依赖改造方案.md)（为何改 ID、BlockManage 同类案例）
- [设计器与 packages 边界约定](./设计器与packages边界约定.md)

---

## 1. 先记住结论（80% 的坑）

官方代码里大量写的是：

```ts
activePlugin(PLUGIN_NAME.Page)          // === META_APP.Page
getMetaApi(META_APP.Page).highlightMethod(...)
```

我们在 `registry.ts` 里的惯用做法是：

```ts
[META_APP.Page]: false,                 // 禁用官方入口
'engine.plugins.customScript': {        // 注册自定义插件（新 ID）
  id: 'engine.plugins.customScript',
  entry: CustomScript,
  apis: ScriptApi
}
```

**迁源码时如果只改了 registry，没全局搜一遍 `META_APP.Xxx` / `PLUGIN_NAME.Xxx`，就会出现：**

| 调用方仍指向 | 实际生效的是 | 表现 |
| --- | --- | --- |
| 官方 ID（如 `engine.plugins.pagecontroller`） | 已 `false` 禁用 / UI 不在左侧栏 | `activePlugin` 改了 `plugins.render`，但**没有对应面板** → 看似「没反应」 |
| 官方 ID 上残留的旧 `apis`（见 §3） | 自定义插件自己的 `apis` 未用到 | 部分读写 schema 碰巧还能用，但**依赖面板实例（Monaco）的 API 必挂** |

**排查第一原则：出问题的功能里，所有 `activePlugin` / `getMetaApi` / `fixed-name` / 布局里的 plugin id，是否与 `registry.ts` 里当前注册的 id 一致？**

## 2. 标准排查步骤（建议按序）

### Step 0：确认是「迁移残留」还是「业务逻辑 bug」

1. 在官方 `packages/` 里找到同名功能，看它怎么写（对照源逻辑）。
2. 在 `designer-demo` 里搜同名函数（如 `openCodePanel`、`highlightMethod`）。
3. 对比两边调用的 **插件 ID** 和 **API 名**。

若官方用 `META_APP.Page`，本地 registry 已换成 `customScript`，而本地仍写 `META_APP.Page` → 基本就是本指南这类问题。

### Step 1：对照 registry 映射表

打开 `designer-demo/registry.ts`，确认：

```text
官方 META_APP.*  === false ?
自定义 id（engine.plugins.customXxx）是否注册？
apis: 是否挂在自定义 id 上？
layout.plugins.left/top 里列的是不是自定义 id？
```

常用映射（以当前工程为准，改 registry 后请同步更新本节）：

| 官方常量 | 官方 ID（约） | 自定义 ID | 备注 |
| --- | --- | --- | --- |
| `META_APP.Page` | `engine.plugins.pagecontroller` | `engine.plugins.customScript` | **Script / Page JS**，不是页面树 |
| `META_APP.State` | … | `engine.plugins.customState` | |
| `META_APP.Schema` | … | `engine.plugins.customSchema` | |
| `META_APP.I18n` | … | `engine.plugins.customI18n` | |
| `META_APP.Bridge` | … | `engine.plugins.customBridge` | |
| `META_APP.Collections` | … | `engine.plugins.customCollections` | Datasource |
| `META_APP.OutlineTree` | … | `engine.plugins.customOutlineTree` | |
| `META_APP.BlockManage` | … | `engine.plugins.customBlockManage` | 去依赖文档里已有案例 |
| `META_APP.Materials` | … | `engine.plugins.customMaterials` | 含子 tab id |
| `META_APP.AppManage` | … | `engine.plugins.singlePage` 等 | 以 registry 为准 |

常量集中处（优先在这里加，避免散落魔法字符串）：

- `src/constants/plugin-ids.ts`（已有 `SCRIPT_PLUGIN_ID`）

### Step 2：全局搜调用点（不要只改「出问题的那一个文件」）

在 `designer-demo/src`（以及同步的 `lowcode-kit/packages/designer/src`）搜索：

```bash
# 以 Script 为例
rg -n "META_APP\\.Page|PLUGIN_NAME\\.Page|pagecontroller" src/

# 通用：某个官方常量
rg -n "META_APP\\.<Name>|PLUGIN_NAME\\.<Name>" src/
```

重点文件类型：

- **跨插件调用方**：settings（如 events）、toolbars、composables、i18n-wrappers
- **插件自身**：`Main.vue` 的 `fixed-name`、`pluginId`
- **layout**：`registry` 里 `layout.plugins` / `settings` 列表

凡是「打开左侧某插件 + 调其 apis」的代码，一律改成自定义 ID。

### Step 3：验证 `getMetaApi` / `activePlugin` 行为

`activePlugin`（layout）逻辑本质是：

```ts
plugins.render = name
nextTick(() => resolve(getMetaApi(name)))
```

`getMetaApi(id)` 读的是注册时写入的 `apisMap[id]`。

调试时可在点击处临时打日志：

```ts
console.log('active', SCRIPT_PLUGIN_ID, getMetaApi(SCRIPT_PLUGIN_ID))
```

期望：

- `getMetaApi(自定义id)` 有 `highlightMethod` / `saveMethod` / `getMethods` 等
- `getMetaApi(META_APP.Page)` 在禁用官方后**不应再作为依赖**（即便偶发还能拿到残留 apis，也不要用）

### Step 4：区分「面板没打开」vs「打开了但没高亮/没副作用」

| 现象 | 更可能原因 |
| --- | --- |
| 左侧栏完全不变 | `activePlugin` 的 id 错了 / 插件未进 layout |
| 面板打开了，代码没跳转 | `highlightMethod` 取错模块实例，或 Monaco 尚未 mount |
| 能保存方法、不能定位 | 读写 schema 的 API 碰巧还能用；依赖编辑器实例的 API 挂了 |

依赖编辑器实例时，可在 `highlightMethod` 内对 Monaco 未就绪做短重试（Locate Code 已加），避免「第一次点只开面板、不高亮」。

## 3. 注册表细节：为什么「官方 API 偶尔还能用」会误导你

`mergeRegistry` 在 `[META_APP.X]: false` 时：

- 会从 `metaHashMap` **删掉**该插件（左侧不再渲染官方面板）
- **不一定清理** `apisMap[官方id]`（若默认 registry 曾注册过官方包）

于是可能出现：

- `getMetaApi(META_APP.Page)` 仍返回**官方包模块**里的 `saveMethod` / `getMethods`（读写的是同一份 page schema，所以绑定事件「看起来正常」）
- 但 `highlightMethod` 操作的是**官方包里未挂载的 Monaco**
- 同时 `activePlugin(META_APP.Page)` 打开的是**已删除的 UI 入口**

→ 业务半残：绑定 OK，Locate Code 全滅。排障时不要因为「半边还能用」就排除 ID 问题。

## 4. 案例：Events「Locate Code」无反应（2026-07）

### 4.1 官方原逻辑（`packages/settings/events`）

```ts
const { highlightMethod } = getMetaApi(META_APP.Page)
const openCodePanel = (action) => {
  activePlugin(PLUGIN_NAME.Page).then(() => {
    highlightMethod?.(action.ref)
  })
}
```

意图：打开 **Page JS（Script）** 插件，并高亮 `action.ref` 对应函数。

### 4.2 迁移后的断裂点

- registry：`[META_APP.Page]: false` + `'engine.plugins.customScript'`
- events 仍调用 `META_APP.Page` / `PLUGIN_NAME.Page`
- BindEventsDialog 里甚至曾直接 `return` 跳过 `highlightMethod`（治标不治本）

### 4.3 修复要点

1. 引入 `SCRIPT_PLUGIN_ID = 'engine.plugins.customScript'`（`src/constants/plugin-ids.ts`）
2. `activePlugin(SCRIPT_PLUGIN_ID)` + `getMetaApi(SCRIPT_PLUGIN_ID)`
3. 同步改 events 对话框、sidebar、content，以及其它仍用 `META_APP.Page` 取 Script API 的地方（如 `useBlock`、`VariableConfigurator`）
4. `highlightMethod`：Monaco 未 mount 时短重试 `setEditorSelection`

涉及目录（designer-demo 与 lowcode-kit 需同步）：

- `src/settings/events/components/BindEvents*.vue`
- `src/plugins/script/js/method.ts`
- `src/constants/plugin-ids.ts`

### 4.4 验收

1. 选中已绑定事件的组件 → Events → 点 `</>`（Locate Code）
2. 左侧打开 Page JS，编辑器滚动并选中对应函数（如 `showDialog`）
3. 新建/编辑事件确认后，也应能打开 JS 并高亮新方法名

## 5. 迁移后自检清单（建议贴进 MR）

- [ ] `registry.ts`：官方 `[META_APP.X]: false`，自定义 id + `apis` 已挂上
- [ ] 插件 `Main.vue`：`fixed-name` / 内部 `pluginId` === 自定义 id
- [ ] 全仓无残留：`getMetaApi(META_APP.X)`、`activePlugin(PLUGIN_NAME.X)`（对该 X）
- [ ] layout 左右栏配置使用的是自定义 id
- [ ] 跨插件调用方（events / save / block / variable…）已改
- [ ] 依赖面板实例的 API（编辑器高亮、focus）在「首次打开面板」路径测过
- [ ] `designer-demo` 与 `lowcode-kit/packages/designer` 已同步（若两边并行维护）

## 6. 推荐改法（避免下次再散落）

```ts
// src/constants/plugin-ids.ts
/** 官方 META_APP.Page 已禁用，Script/Page JS 使用此 ID */
export const SCRIPT_PLUGIN_ID = 'engine.plugins.customScript'
// 后续可继续补：STATE_PLUGIN_ID、I18N_PLUGIN_ID ...
```

调用处：

```ts
import { SCRIPT_PLUGIN_ID } from '@/constants/plugin-ids'

activePlugin(SCRIPT_PLUGIN_ID).then(() => {
  nextTick(() => {
    const { highlightMethod } = getMetaApi(SCRIPT_PLUGIN_ID) || {}
    highlightMethod?.(methodName)
  })
})
```

**不要**在业务里继续写 `META_APP.Page`「碰巧能拿到 apis」——UI 与 API 必须同一套自定义 id。

## 7. 快速决策树

```text
功能点了没反应？
  ├─ 官方 packages 里该功能是否依赖 activePlugin / getMetaApi？
  │     └─ 是 → 本地 registry 是否把该 META_APP 设成 false 并换了 custom* id？
  │           └─ 是 → 全仓搜旧 ID，改成 custom*（优先加 constants）
  ├─ 面板能开但编辑器操作无效？
  │     └─ 检查是否调到了「另一份」plugin 模块的 apis；检查 Monaco/DOM 是否已 mount
  └─ 与插件 ID 无关？
        └─ 再查 props、schema、i18n、事件名等业务逻辑
```
