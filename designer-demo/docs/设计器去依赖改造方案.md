# TinyEngine 设计器去依赖改造方案

## 项目背景

当前 TinyEngine 设计器（designer-demo）依赖 mockServer 提供接口数据，包括：

-   页面加载数据
-   组件库加载
-   区块加载
-   用户信息获取

目标是将设计器改造为不依赖任何后端接口，通过 VS Code 扩展程序传递数据，实现设计器的独立运行。

## 接口依赖分析

### 1. 核心接口分组

#### platform-center 接口

-   **`/platform-center/api/user/me`**
    -   用途：获取登录用户信息
    -   调用位置：`GlobalService` 初始化时
    -   影响：用户头像、权限判断
    -   替代方案：VS Code 扩展返回静态用户对象

#### app-center 接口

-   **读取类接口**：

    -   `/app-center/api/apps/list/:platformId` - 应用列表
    -   `/app-center/api/apps/detail/:id` - 应用详情
    -   `/app-center/v1/api/apps/schema/:id` - 应用 Schema（核心）
    -   `/app-center/api/pages/list/:appId` - 页面列表
    -   `/app-center/api/pages/detail/:id` - 页面详情
    -   `/app-center/api/pages/histories` - 页面历史

-   **写入类接口**：
    -   `/app-center/api/apps/update/:id` - 更新应用
    -   `/app-center/api/pages/create|update|copy|delete` - 页面 CRUD
    -   `/app-center/api/schema2code` - 代码生成
    -   `/app-center/api/apps/publish/:id` - 发布应用

#### material-center 接口

-   **区块管理接口**：
    -   `/material-center/api/block-groups` - 区块分组
    -   `/material-center/api/block?label=...` - 区块查询
    -   `/material-center/api/block/detail/:id` - 区块详情
    -   `/material-center/api/block/create|update|delete` - 区块 CRUD

## 改造方案

### 1. VS Code 扩展数据提供方案

#### 扩展侧实现

```javascript
// VS Code 扩展中注入 window.vscodeBridge
window.vscodeBridge = {
    request: async ({ url, method, params, data }) => {
        // 路由到本地文件系统操作
        switch (url) {
            case '/platform-center/api/user/me':
                return { id: 'vscode-user', name: 'VS Code User' };

            case '/app-center/v1/api/apps/schema/:id':
                return await readAppSchemaFromWorkspace(id);

            case '/app-center/api/pages/list/:appId':
                return await readPagesFromWorkspace(appId);

            case '/app-center/api/pages/detail/:id':
                return await readPageFromWorkspace(id);

            case '/app-center/api/pages/update/:id':
                return await writePageToWorkspace(id, data);

            default:
                throw new Error(`Unsupported API: ${url}`);
        }
    }
};
```

#### 前端适配

```javascript
// designer-demo/src/composable/http/index.js
const createVSCodeAdapter = () => {
    return async config => {
        if (window.vscodeBridge) {
            const response = await window.vscodeBridge.request({
                url: config.url,
                method: config.method,
                params: config.params,
                data: config.data
            });
            return { data: { data: response } };
        }
        return axios(config);
    };
};

// 在 axios 配置中使用自定义 adapter
const customizeHttpService = () => {
    const options = {
        axiosConfig: {
            ...getConfig(),
            adapter: createVSCodeAdapter()
        },
        interceptors: {
            request: [preRequest],
            response: [[preResponse, errorResponse]]
        }
    };
    HttpService.apis.setOptions(options);
    return HttpService;
};
```

## 技术可行性评估

### ✅ 高可行性

-   **现有架构支持**：代码已有 VS Code 环境判断和通道占位
-   **HTTP 服务集中**：统一在 `HttpService` 中，便于改造
-   **物料本地化**：已支持本地 `bundle.json` 文件

### ⚠️ 中等风险

-   **复杂功能依赖**：发布、数据源管理等需要后端逻辑
-   **文件格式规范**：需要定义本地文件存储格式
-   **插件兼容性**：部分插件可能依赖特定接口

### 🔧 解决方案

-   **分阶段实施**：先实现核心功能，复杂功能后续补齐
-   **标准化格式**：定义统一的本地文件格式规范
-   **插件隔离**：非核心插件在 VS Code 模式下禁用

## 预期效果

## 插件迁移实践案例

### Block 插件迁移经验

#### 迁移背景

Block 插件是设计器中的核心功能，负责区块管理、编辑和发布。在去依赖改造过程中，我们成功将其从官方插件迁移为自定义插件。

#### 迁移步骤

##### 1. 插件注册替换

```typescript
// registry.ts
export default {
    // 禁用官方 BlockManage
    [META_APP.BlockManage]: false,
    // 使用自定义 BlockManage
    'engine.plugins.customBlockManage': {
        id: 'engine.plugins.customBlockManage',
        title: 'BlockManage',
        type: 'plugins',
        icon: 'plugin-icon-symbol',
        entry: CustomBlockManage,
        options: {
            mergeCategoriesAndGroups: true
        },
        metas: [BlockService],
        components: {
            SaveNewBlock
        }
    }
};
```

##### 2. API 引用更新

-   **问题**：代码中仍在使用官方 API 引用
-   **解决**：将所有 `getMetaApi(META_APP.BlockManage)` 替换为 `getMetaApi('engine.plugins.customBlockManage')`
-   **影响文件**：
    -   `useBlock.ts`
    -   `src/toolbars/save/js/index.ts`

##### 3. 国际化完整实现

-   **硬编码文字替换**：将所有中文硬编码文字替换为 `t()` 函数调用
-   **响应式标签**：将静态标签对象改为 `computed` 属性，确保语言切换时自动更新
-   **文字优化**：缩短过长的文字，避免显示省略号

##### 4. 组件结构优化

-   **移除无用导入**：删除 `<script setup>` 中不需要的 `defineEmits`、`defineProps` 导入
-   **错误处理**：添加国际化键值缺失时的降级处理

#### 技术要点

##### 1. 插件注册机制

-   使用 `META_APP.BlockManage: false` 禁用官方插件
-   通过自定义 ID 注册新插件
-   保持相同的接口和功能

##### 2. API 兼容性

-   确保自定义插件提供与官方插件相同的 API
-   更新所有引用点，避免回退到官方实现

##### 3. 国际化最佳实践

-   使用 `computed` 属性确保响应式更新
-   提供降级处理机制
-   优化文字长度，提升用户体验

#### 迁移效果

##### ✅ 成功实现

-   完全独立运行，不依赖官方插件
-   国际化功能完整，支持中英文切换
-   保持原有功能完整性
-   代码结构清晰，易于维护

##### 📝 经验总结

1. **插件替换**：禁用官方插件 + 注册自定义插件
2. **API 更新**：确保所有引用点都使用新的插件 ID
3. **国际化**：使用响应式属性，避免静态文字
4. **文字优化**：控制长度，提升用户体验

> 同类问题的系统排查（含 Events Locate Code / `META_APP.Page` → `customScript`）见：[迁移插件功能失效排查指南](./迁移插件功能失效排查指南.md)

### I18n 插件迁移实践案例

#### 迁移背景

I18n 插件是设计器中的国际化资源管理插件，负责管理多语言翻译数据。在去依赖改造过程中，我们成功将其从官方插件迁移为自定义插件。

-   **响应式设计**：设置 min-width 和 max-width 保持一致

基于 Block 和 I18n 插件的成功迁移经验，建议按照分阶段实施的方式推进，先实现核心功能，再逐步完善其他特性。插件迁移的关键经验总结：

### 插件迁移模式总结

基于 Block、I18n 和 State 插件的迁移经验，可以总结出以下迁移模式：

#### 模式一：有服务依赖插件（如 Block、I18n）

-   需要导出和注册 meta 服务
-   在 registry.ts 中配置 metas
-   相对复杂，需要处理服务依赖

#### 模式二：无服务依赖插件（如 State）

-   直接使用 Main.vue 作为入口
-   无需 meta 服务配置
-   迁移更简单，配置更少

#### 通用原则

1. **保持原始结构**：直接复制原始文件，避免修改核心代码
2. **清理构建文件**：删除独立包相关文件
3. **简化入口文件**：创建简化的 index.ts
4. **正确注册配置**：在 registry.ts 中正确配置插件
5. **布局位置设置**：在 Layout 配置中设置插件位置

这种分类化的迁移方法为不同类型的插件提供了针对性的迁移策略。

## RedoUndo 迁移排障复盘（VSCode 定制链路）

### 现象与影响

-   现象 1：顶部撤销/恢复按钮长期置灰，修改属性后仍显示 `Nothing to undo`
-   现象 2：部分阶段可撤销但会卡在“应用数据初始化中...”
-   现象 3：部分阶段 `undo` 生效但 `redo` 无反应
-   影响：编辑链路不稳定，误以为画布或插件整体失效

### 核心根因（最终确认）

1. **History hook 覆盖方式不稳定**
    - 仅依赖 `registry` 的服务覆盖时，可能出现状态与方法不是同一闭包实例的风险（表现为按钮事件命中但状态不联动）。
2. **过度兜底导致历史语义被破坏**
    - 自动轮询入栈、事件订阅强制入栈会污染历史栈，尤其在 `undo` 后容易吃掉前进分支，导致 `redo` 失效。
3. **去依赖改造后的定制链路与官方行为有差异**
    - 必须保留 `resetCanvasState(..., loading:false)` 兼容，否则可能回到初始化态。

### 最终稳定方案

#### 1) 启动阶段强制替换 `useHistory` hook（推荐）

在 `designer-demo/src/main.ts` 的 `beforeAppCreate` 中，通过 `initHook(..., { useDefaultExport: true })` 直接替换：

```ts
initHook(hookNameMap.useHistory, customUseHistory, {
    useDefaultExport: true
});
```

> 说明：该方式绕过 registry 深度合并副作用，保证 `useHistory()` 始终命中自定义实现。

#### 2) `useHistory` 回归官方语义，仅保留必要兼容

文件：`designer-demo/src/toolbars/redoundo/composable/useHistory.ts`

-   保留官方核心行为：
    -   `addHistory()` 入栈
    -   `go(-1/1)` 只移动历史指针
    -   新操作会截断前进栈（标准 undo/redo 语义）
-   保留定制兼容：
    -   `resetCanvasState` 时显式传 `loading:false`
-   移除不稳定逻辑：
    -   自动轮询入栈
    -   事件订阅强制入栈
    -   与历史语义冲突的额外栈修补逻辑

#### 3) 调整历史容量

-   `maxLength` 由较小值提升到更合理容量（当前为 `20`），减少“很快没得撤销”的体验问题。

### 回归测试用例（建议固化）

1. 打开页面（记录初始状态）
2. 拖拽 `MpInputContent` 到新位置
3. `undo` 一次：回到拖拽前
4. `redo` 一次：回到拖拽后
5. 再做一次新编辑后点击 `redo`：应无反应（前进栈被新分支截断，属正常）

### 排障经验（避免重复踩坑）

-   优先验证“是否命中同一条 hook 链路”，再改业务逻辑。
-   对 undo/redo 问题，先守住历史语义，不要先加自动入栈兜底。
-   定制环境下可加最小可观测信息，但最终应回收调试噪音，避免长期维护负担。
-   若出现“能 undo 不能 redo”，优先检查是否存在回放期间额外入栈行为。
