# 业务组件与原子组件导入设计器方案（主工程产物模式）

> **本文只描述当前推荐的「主工程产出物料包 + 设计器加载」方案。**  
> 早期在 designer-demo 仓库内维护 `materials-src` 并本地构建物料的旧流程，已单独挪到 `docs/业务与原子组件导入方案-旧流程.md` 中，仅作历史参考。  
> 主工程内关于设计时兼容版组件的详细规范，请以各主工程仓库的 `lowcode-materials/README.md` 与 `lowcode-materials/DESIGN_TIME_COMPAT.md` 为准。
>
> **导入组件必守规则（仍然适用）**：① **图标**：物料需配置 `icon` 或使用默认图标；② **分组**：`group` 使用 `"原子组件"` / `"业务组件"`，英文面板由设计器自动翻译；③ **名称**：`name` 必须包含 `zh_CN` 与 `en_US`。

---

## 一、整体架构概览

当前推荐的物料接入模式可以简单概括为：

-   **主工程负责产出物料包**：

    -   在主工程仓库中建立 `lowcode-materials/` 目录，内含：
        -   `design-components/`、`canvas-stubs/`：设计时兼容版组件与画布桩；
        -   `entries/`：物料入口（每个组件一个 entry 文件）；
        -   `scripts/`：提取设计 token / 公共样式 / 组件样式、生成 bundle 的脚本；
        -   `manifest.json`：物料清单，描述有哪些组件、脚本文件名、schema 等。
    -   通过主工程脚本（如 `pnpm run build:designer-materials`）完成：
        -   运行提取脚本（design tokens、canvas 样式、公共样式、icon 资源）；
        -   使用专用 Vite 配置构建物料 ESM / CSS；
        -   生成符合物料协议的 `dist/lowcode-materials/bundle.json`。

-   **设计器与 VSCode 插件只负责「加载物料包」**：

    -   设计器浏览器版通过 `engine.config.material` 配置 bundle URL：
        -   例如：`material: ["/mock/bundle.json", "http://localhost:3000/bundle.json"]`。
    -   VSCode 插件通过配置项 `lowcode-designer.materialBundleUrls` 注入：
        -   在 webview 中写入 `window.TINY_MATERIAL_BUNDLE_URLS = ["http://localhost:3000/bundle.json"]`；
        -   设计器在启动时合并这些 bundle，与自身内置 bundle 一起加载。

-   **出码仍然使用主工程真实组件**：
    -   设计时兼容版组件（`*-designer.vue`、`*-canvas.vue`）只在画布运行；
    -   物料协议中的 `component` / `npm.package` / 代码生成规则仍然指向主工程真实组件，保证生成项目与运行环境一致。

### 1.1 角色划分

-   **主工程**（如 `mobilebanking`）：
    -   真实业务组件的**唯一真相来源**；
    -   负责实现设计时兼容版组件、生成物料 bundle。
-   **设计器工程**（`designer-demo`）：
    -   独立部署的低代码设计器前端；
    -   只负责**加载物料包并在画布中渲染**，不再维护业务组件源码。
-   **VSCode 插件**（`lowcode-kit/packages/vscode`）：
    -   提供 webview 容器与配置；
    -   将 `developmentServerUrl` 与 `materialBundleUrls` 等信息注入 webview，协助设计器在插件环境下加载物料。

### 1.2 目标

-   设计器不再复制主工程源码，只加载主工程产出的 bundle；
-   设计时组件在画布中的观感**尽量接近真实运行效果**；
-   引入新业务组件时，主要在主工程内操作，设计器侧只需调整物料 URL 或升级扩展。

---

### 1.1 目的

本文档总结将**业务组件（mp 开头）**与**原子组件（mr 开头）**导入 TinyEngine 设计器（designer-demo）的可行性、推荐方案与实施流程，供后续具体落地与开发参考。

### 1.2 背景

-   **业务组件**：如 `mp-card`，位于业务项目（如 mobilebanking）`src/components` 下，以源码形式维护，未发布为 npm 包。
-   **原子组件**：如 `mr-divider`，通过 resolver 将 **Vant**、**Ionic** 等库的组件映射为 mr 前缀命名，在业务组件中被广泛引用。
-   **需求**：
    -   在设计器中可拖拽使用业务组件（mp-\*）。
    -   在设计器中可拖拽使用原子组件（mr-\*）。
    -   业务组件内部对原子组件的依赖在设计器画布与预览中能正确解析并渲染。
    -   方案尽量简单、不繁琐，便于持续接入新组件。

## 二、可行性结论摘要

### 2.1 物料资产包与「npm」的含义

-   设计器通过 `engine.config.material` 配置的 bundle（如 `/mock/bundle.json`）加载物料；支持**多个物料源**（数组）。
-   协议中的 **npm** 字段表示「组件来源的元数据」（包名、脚本地址、导出名等），**不要求**组件一定从 npm 仓库安装。
-   画布通过 `npm.script` 的 URL 动态 `import(script)` 加载组件；**script 可为任意可访问的 ESM 地址**（含本地路径），不限于 CDN。

因此：**用源码构建出的 ESM + 在 bundle 中正确配置 npm（含 script、exportName 等），即可在设计器中使用，无需发布 npm 包。**

### 2.2 业务组件（源码形态）接入

-   **可行**：将业务组件（如 mp-card）构建为 ESM（如 `mp-card.js`），部署到设计器可访问的路径，在物料包中为该组件配置一条记录，`npm.script` 指向该 ESM，`npm.package` 使用占位符（如 `@local/mp-card`）。
-   **bundle 配置**：每个要在设计器中使用的组件，都必须在物料包的 `components` 与 `snippets` 中各有一条对应配置；可沿用现有「单组件 JSON + buildMaterials 合并」机制，便于批量维护。

### 2.3 原子组件（Vant / Ionic）在设计器中的必要性

-   业务组件内部会引用原子组件（如 mp-card 使用 mr-divider）；若设计器环境**不提供**这些依赖，加载业务组件时会报错或无法渲染。
-   同时，若希望原子组件也能在设计器中**单独拖拽使用**，设计器必须提供其实现（Vant / Ionic 或统一封装）。
-   **原子组件来源**：mr-\* 既有来自 **Vant**（如 mr-divider），也有来自 **Ionic**，需统一考虑，避免设计器侧配置多套、重复且难以维护。

## 三、推荐方案：统一 mr 原子组件入口（Vant + Ionic）

### 3.1 思路

-   **设计器只维护一份「原子组件」运行时**：一个 ESM，内部从 **Vant** 和 **Ionic** 按需引入组件，并以 **mr 命名**统一 re-export（与业务项目中的 resolver 命名一致）。**主工程用哪个库的原子组件，设计器就提供哪个**：该用 Vant 用 Vant、该用 Ionic 用 Ionic，保证画布与主工程一致。
-   **原子组件**：在物料中为每个 mr-\* 配置一条，`npm.script` 均指向该统一入口，仅 `exportName` 不同。
-   **业务组件**：构建时将这一份入口作为 **external**，不把 Vant/Ionic 打进业务组件 ESM；运行时由设计器提供的同一份脚本解析所有 mr-\*。

这样实现：

-   设计器只需配置**一个**脚本 + Vant 与 Ionic 的样式，逻辑简单。
-   原子组件与业务组件共用同一套依赖，无重复、无两套来源。
-   后续新增第三方 UI 库时，只需在统一入口中增加 re-export，设计器配置可保持不变。

### 3.2 与「业务组件自包含」的对比

若采用「每个业务组件 ESM 内打包 Vant/Ionic」：

-   原子组件若要单独拖拽，设计器仍需再提供一份 Vant/Ionic（或 mr 入口）。
-   结果：设计器内存在两套 Vant 来源（一份给原子物料、一份被打进各业务组件），体积与维护成本都增加。

因此，在**原子组件也需导入设计器并拖拽使用**的前提下，推荐**不**采用业务组件自包含，而是采用**设计器统一提供一份 mr 入口，原子与业务组件共同复用**。

### 3.3 为何用「一个入口」同时接 Vant 和 Ionic

-   若设计器分别配置 Vant 和 Ionic：需维护两个库、两套样式，原子物料要按来源选择不同 script，业务组件构建也要 external 两个包，流程更复杂。
-   采用**一个 mr 入口（内部再接 Vant 和 Ionic）**：设计器只配置「一个脚本 + 两套样式」，原子与业务组件都只依赖这一入口，**简单、不繁琐**，且与「尽量简单」的目标一致。

## 四、方案流程与实施要点

### 4.1 设计器侧：提供统一 mr 原子组件入口与样式

1. **维护一个 ESM**（如 `mr-components.js`，名称可自定）：
    - 从 **Vant** 引入主工程用到的组件，按 mr 命名 re-export（例：`export { Divider as MrDivider } from 'vant'`）。
    - 从 **Ionic** 引入主工程用到的组件，同样按 mr 命名 re-export（例：Segment、SegmentButton、Label 等）。
    - **原则**：主工程原子组件基于 Vant 或 Ionic，设计器侧**该用哪个就用哪个**，与业务项目（mobilebanking）中 resolver 的映射保持一致（组件名、使用的具体子组件），保证画布效果与真实运行一致。
2. **部署**：将该 ESM 部署到设计器/预览可访问的 URL（如 `designer-demo/public/mock/materials/mr-components.js`）。
3. **设计器加载方式**：通过 import map 或物料依赖配置，使画布能解析该入口（如配置为 `@your/mr-components` 或对应 URL）。
4. **样式**：在设计器/预览中加载 **Vant 样式** 与 **Ionic 样式**（可两个 link，或合并为一个），否则原子组件会缺样式。

### 4.2 原子组件：作为物料录入

1. 对每个需要在设计器中拖拽的 mr-\*（如 mr-divider、mr-button 等），在物料包（主 bundle 或单独业务物料 JSON）中新增一条：
    - `component`：画布使用的组件名（如 `MrDivider`）。
    - `npm`：`package` 占位（如 `@local/mr-components`），`script` 指向上述统一入口 URL，`exportName` 与入口中的导出名一致（如 `MrDivider`）。
    - `schema`、`configure`、`snippets` 按需配置（可与现有 Tiny 组件类似结构）。
2. 所有原子组件物料共用**同一个** `npm.script`，仅 `exportName` 不同。

**为何 MrDivider 能用、mr-img 导致 MpImage 不显示？** 因为 MrDivider 是**物料**且实现来自 Vant（纯 DOM+CSS），而主工程里 `<mr-img>` 实际是 **Ionic 的 ion-img**；若设计器未引入 Ionic 或 mr 入口只导出 Vant Image，画布内 mr-img 无法渲染。推荐**设计器同时引入 Vant 与 Ionic**，在 **mr-components.js 中引入 Ionic 并 export MrImg**（与主工程一致），画布注入 Ionic 后即可用；原子尽量用第三方源码，不造桩（见 [组件导入注意事项.md](./组件导入注意事项.md)）。

### 4.3 业务组件：构建与物料配置

1. **构建**：
    - 将业务组件（如 mp-card）构建为 ESM（如 `mp-card.js`），部署到设计器可访问路径（如 `designer-demo/public/mock/materials/mp-card.js`）。
    - 构建时把 **mr 原子组件入口**（或 Vant/Ionic）设为 **external**，不打包进业务组件；产物中对 mr-\* 的 import 指向该统一入口（通过 alias/resolver 在构建时配置）。
2. **物料配置**：
    - 在物料包中为每个业务组件配置一条：`component`、`npm`（`package` 占位、`script` 指向该业务组件 ESM、`exportName` 等）、`schema`、`configure`、snippet 等。
    - 与现有「单组件 JSON + buildMaterials 合并」机制保持一致，便于批量维护与扩展。

### 4.4 物料源与 bundle 组织（可选）

-   `engine.config.material` 支持数组，可配置多个物料源，例如：
    -   `["/mock/bundle.json", "/mock/business-materials.json"]`
-   建议：基础/内置组件继续使用现有 `bundle.json`；业务组件与原子组件可放在同一 bundle，或单独使用 `business-materials.json`，便于与基础物料解耦、独立迭代。

### 4.5 插件环境（VSCode webview）下的 URL 处理

-   物料包 JSON 中的 `script` 通常为相对路径（如 `/mock/materials/mp-card.js`）。在**浏览器**中画布 iframe 的 base 与设计器一致，相对路径可解析；在 **VSCode 插件 webview** 中 iframe 的 base 为 `vscode-webview://...`，相对路径会被解析到错误协议导致 403。
-   designer-demo 在插件环境下通过 **`src/composable/canvasDepsNormalizer.ts`** 订阅 `init_canvas_deps`，将相对路径转为「设计器前端绝对 URL」（如 `http://localhost:8090/mock/materials/mp-card.js`）后重新发布，画布拿到的即为可加载的绝对 URL；同时 `designerOrigin`、`useMaterial.getCanvasDeps`、`CanvasContainer` 在设计器侧发布依赖时也使用绝对 URL。因此**同一套物料配置**在浏览器与插件中均可使用，无需在物料 JSON 里写死绝对 URL。详见 `docs/VSCode-Integration.md` 中「固定 Mock 与物料包」「为什么导入的物料在插件中需要绝对 URL」等小节。

### 4.5.1 主工程物料在画布中的 Import Map（设计器加载主工程 bundle 时）

-   当物料来自**主工程 bundle**（如 `http://localhost:3000/bundle.json`）时，画布 iframe 内加载的组件脚本会 `import ... from '@local/mp-card'` 或 `'mp-card.js'` 等。浏览器要求 **import map 的 value 必须是完整 URL**，不能是裸说明符（bare specifier，如 `"mp-card.js"`），否则会报 `Ignored an import map value... Bare specifier` 且产生 `Failed to resolve module specifier 'mp-card.js'`。
-   设计器在 **`CanvasContainer.vue`** 的 iframe srcdoc 中：（1）**移除**引擎/画布内可能已存在的 import map（其 value 常为裸说明符）；（2）**注入唯一** import map，将当前物料依赖中的 `@local/*` 与 `*.js` 全部映射为**完整 URL**（来自 `materialsDeps.scripts` 的绝对地址或由设计器 base 拼出）。这样设计器自有物料与主工程物料在画布内均可正确解析，无需改引擎包。

### 4.6 新增组件时的规则（保持简单）

-   **新增原子组件**：在 mr 入口中增加对应 re-export；在物料中增加一条原子组件配置，`npm.script` 指向同一 mr 入口。
-   **新增业务组件**：构建出对应 ESM 并部署；在物料中增加一条业务组件配置；构建时保持对 mr 入口的 external。
-   **不引入**「业务组件自包含 + 设计器再单独供一份原子」的双重依赖，避免重复与复杂化。

### 4.7 导入组件的图标与国际化规则（必遵守）

所有导入设计器的业务组件与原子组件，需满足以下约定，以保证物料面板与画布展示一致、且支持中英文切换。

#### 4.7.1 图标

-   **必须配备图标**：每条物料配置需提供 **`icon`** 字段（字符串，如 `"card"`、`"split"`），对应设计器内已注册的 SVG 图标名（小写）。
-   **图标来源**：
    -   设计器内置图标：来自 `@opentiny/tiny-engine` 的 assets（如 `row`、`box`、`slot`、`table` 等），可直接作为 `icon` 使用。
    -   自定义图标：在 **designer-demo/src/assets/icons/** 下新增同名 `.svg` 文件（如 `card.svg`、`split.svg`），即可在物料中写 `"icon": "card"`；未配置 `icon` 或图标名不存在时，面板会使用默认图标 `component-default`。
-   **新增组件时**：若希望专用图标，在物料 JSON 中写 `"icon": "xxx"`，并在 `src/assets/icons/` 下新增 `xxx.svg`；否则可不写 `icon`，将使用默认图标。

#### 4.7.2 分类与面板标题

-   **分类约定**：原子组件（mr 开头）归为 **原子组件**，业务组件（mp 开头）归为 **业务组件**。物料 JSON 中 **`group`** 字段只填中文键：`"原子组件"` 或 `"业务组件"`。
-   **面板显示**：设计器按当前语言自动映射为：
    -   中文：**原子组件** / **业务组件**
    -   英文：**MR Components** / **MP Components**
-   无需在物料中写英文分组名，由设计器统一做国际化。

#### 4.7.3 组件名称（物料面板与画布）

-   **必须提供双语**：每条物料的 **`name`** 必须为对象，且包含 **`zh_CN`** 与 **`en_US`**，例如：
    ```json
    "name": { "zh_CN": "卡片", "en_US": "Card" }
    ```
-   **面板与画布**：物料面板中的组件名称、以及拖拽到画布后的展示名称，均按设计器当前语言（中文/英文）自动切换；未提供 `en_US` 时英文环境下会回退到 `zh_CN`。
-   **命名建议**：`en_US` 使用简短英文（如 Card、Divider、Progress），与组件语义一致，便于英文用户识别。

## 五、实施时注意事项（不写具体代码，仅要点）

1. **mr 入口与业务项目 resolver 一致**：命名、使用的 Vant/Ionic 子组件尽量与 mobilebanking 一致，避免行为差异。
2. **样式**：Vant、Ionic 的样式均需在设计器/预览中加载；可通过物料 `npm.css` 或预览入口统一引入。
3. **版本**：mr 入口所依赖的 Vant、Ionic 版本建议与业务项目一致或兼容。
4. **按需导出**：mr 入口可只导出设计器实际会用到的原子组件，减小体积。
5. **出码**：若出码逻辑会把 `npm.package`/version 写入生成项目的 package.json，对 `@local/xxx` 这类占位包需在出码侧单独处理（如不写入或写为本地 path），与「在设计器内使用」的可行性无关。

## 六、小结

| 项目         | 结论                                                                                                                                                 |
| ------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------- |
| 业务组件导入 | 通过「主工程构建 ESM + 物料配置」可行，无需发布 npm。                                                                                                |
| 原子组件导入 | 需主工程提供统一 mr 入口；推荐「一个 mr 入口」同时接 Vant 与 Ionic。                                                                                 |
| 推荐方案     | 主工程统一提供一份 mr 原子组件入口（+ 主题样式与公共样式）；原子与业务组件均复用该入口。                                                             |
| 流程         | 主工程构建物料（含设计时兼容组件）并产出 `bundle.json` → 设计器 / VSCode 插件通过 URL 加载 bundle → 画布渲染设计时组件，出码仍指向主工程真实组件。   |
| **复杂组件** | 依赖 Store、$t、路由/i18n 时，主工程在 `lowcode-materials` 内提供 canvas-stubs 与运行时桩；设计器侧通过 import map 与 runtime 安装对齐这些桩的签名。 |
| 目标         | 简单、不繁琐；画布可看可配、出码用主工程；一套依赖、一套规则，便于持续接入新组件。                                                                   |

本文档聚焦当前推荐的主工程产物模式。若需了解历史上的本地构建流程，请参考 `docs/业务与原子组件导入方案-旧流程.md`。

## 七、复杂组件导入与运行时兼容层

本节总结**依赖主工程 Store、全局方法（$t、$currency）、路由、i18n 等**的复杂业务组件的导入经验，以及设计器侧**运行时兼容层（runtime）**的定位与使用方式。

### 9.1 目的与思路

**目标**：

-   **画布效果**：设计器画布/预览中，复杂组件能按与主工程一致的**结构和展示**渲染（如账户项、金额格式化、多 tab 选择等），便于搭建与走查。
-   **出码结果**：出码生成的是**主工程代码**，引用主工程组件与真实依赖（Pinia、$t、vue-router、vue-i18n 等），**不包含**设计器专用兼容层。
-   **接入成本**：复杂组件的**调用方**通常很简单（传参、绑事件）；设计器侧通过「兼容层 + 最小桩」让组件在画布可运行，避免每导入一个组件就重写一套逻辑。

**思路**：

-   在设计器/预览负责渲染画布的 Vue 应用上，挂载一套与主工程**同签名**的接口（全局方法、Pinia store 等），仅提供**只读/展示用**的实现（桩）。
-   物料构建时，复杂组件通过 **@local/runtime** 或 **vue-router / vue-i18n 别名** 使用这些桩；画布内组件与主工程写法一致，出码时仍生成主工程真实引用。

### 9.2 兼容层是什么、放在哪、做什么

**兼容层**即设计器侧的**运行时桩**，代码目录：**`designer-demo/src/runtime/`**。

| 内容                         | 说明                                                                                                                                                                                                                                                           |
| ---------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **globals**                  | 与主工程 `globalProperties` 同签名：`$t`、`$currency`、`$getCurrency`、`$getCurrencySymbol`。仅用于画布展示（如 $t 走设计器 i18n 或回退 key，$currency 做千分位等）。                                                                                          |
| **stores/**                  | Pinia 桩 store，与主工程 **同 store id**（如 `common.account`、`common.payment`），供画布内 `useAccountStore()`、`usePaymentStore()` 等调用；只暴露画布展示所需最小字段/方法（如 `maskBalance`、`checkPaymentway`、`getPaymentWay`、`calcPaymentWayAmount`）。 |
| **vueRouterStub / i18nStub** | 对 `vue-router`、`vue-i18n` 的桩（如 `useRoute()` 返回 `{ query: {} }`，`useI18n()` 的 `t` 走全局 `$t`），物料构建通过 **vite alias** 指向这些文件，避免画布加载主工程路由/i18n。                                                                              |

**挂载时机**：在画布/预览所用 Vue 应用的 **app 创建后、mount 前**，调用 **`installRuntimeCompat(app)`**（见 `src/runtime/index.ts`）。当前在设计器主入口 **main.ts** 与 **preview.ts** 的 `lifeCycles.appCreated({ app })` 中安装，保证画布与预览共用同一套兼容层。

**原则**：

-   兼容层**不实现**真实业务逻辑，只提供「能跑、能看」的最小实现。
-   新组件用到新的 store 或全局方法时，在 runtime 中**按需增加**对应桩即可，逐步丰富，便于后续复杂组件导入越来越容易。

### 9.3 复杂组件导入时的依赖顺序与检查

**规则**：**被依赖的组件与能力必须先于当前组件就绪。**

1. **先检查组件内部依赖**
    - 看主工程该组件的 template 与 script：用到了哪些 **mp-xxx / mr-xxx**、哪些 **store**、哪些 **全局方法**（$t、$currency 等）、**vue-router / vue-i18n**。
2. **组件依赖**
    - 若依赖其他 **mp-xxx**（如 mp-account-picker 依赖 mp-popup、mp-account-item、mp-empty），则这些组件需先在 **materials-src** 中存在，并在 **materials-manifest.json** 的 `components` 中**排在当前组件前面**（设计器会按顺序加载/注册）。
    - **仅作为子组件、不在面板展示**：若某组件只被其他组件内部使用、无单独拖拽场景（如 mp-account-item、mp-account-picker 仅作为 mp-account-input 的组成部分），可在 manifest 中为该条增加 **`"hiddenInPanel": true`**，执行 `pnpm run generate:materials-json` 后该组件不会出现在物料面板，但仍会参与构建与运行时加载。
3. **运行时依赖**
    - 若依赖 Pinia store：在 **runtime/stores** 中提供同 id 的桩，并在 **runtime/index.ts** 的 `installRuntimeCompat` 中通过 `app.use(pinia)` 注册（已统一安装 Pinia 时无需再改）。
    - 若依赖 **$t / $currency** 等：已在兼容层 `globals` 中挂到 `app.config.globalProperties`，画布内可直接使用。
    - 若依赖 **vue-router / vue-i18n**：在主工程 **lowcode-materials/runtime** 下提供桩，并在主工程 **vite.lowcode-materials.config.ts** 的 `resolve.alias` 中把 `vue-router`、`vue-i18n` 指向桩，物料构建时会打包桩而非主工程依赖。
4. **原子组件与主工程一致：该用 Vant 用 Vant、该用 Ionic 用 Ionic**
    - 主工程的原子组件（mr-\*）基于 **Vant** 或 **Ionic**，设计器侧应**与主工程保持一致**：主工程用哪个库的组件，设计器就在 mr 入口（或对应物料）里提供同一来源的组件，该用 Vant 用 Vant、该用 Ionic 用 Ionic，保证画布效果与真实运行一致。
    - **推荐**：在 **materials-src/mr-components.js**（或设计器统一的 mr 入口）中，按主工程 resolver 的映射，从 Vant 与 Ionic 分别引入并 re-export 主工程用到的 mr-\*（如 MrSegment、MrSegmentButton、MrLabel 来自 Ionic，MrDivider、MrProgress 来自 Vant）。这样业务组件无需改写法，画布与主工程表现一致。
    - **例外**：若某库（如 Ionic）暂时尚未接入设计器、且接入成本较高时，可先用**简易等价实现**（如 div + button + 样式）做**临时占位**，让复杂组件先能跑通；后续应补齐真实组件，避免画布与主工程长期不一致。

**实操顺序建议**：先加「被依赖的 mp-xxx / 桩」→ 再在 manifest 中登记并排在前面 → 最后加当前组件并执行 generate + build。

### 9.4 如何按需扩展兼容层

-   **新增全局方法**：在 **runtime/globals.ts** 中实现与主工程同签名的函数，在 **runtime/index.ts** 的 `installRuntimeCompat` 里挂到 `app.config.globalProperties`（如 `$fd`、`$http` 等）。
-   **新增 Pinia 桩**：在 **runtime/stores/** 下新建文件（如 `xxx.ts`），用 `defineStore('主工程 store id', () => { ... })` 暴露最小字段/方法，在 **stores/index.ts** 中导出；无需改安装逻辑，画布内即可通过 `useXxxStore()` 使用。
-   **新增路由/i18n 等桩**：在主工程 **lowcode-materials/runtime/** 下新增桩文件，并在主工程 **vite.lowcode-materials.config.ts** 的 `resolve.alias` 中把对应包名指向该文件；仅依赖该包的物料会使用桩。

保持「按需、最小」原则，避免兼容层承担真实业务，便于维护。

### 9.5 与出码的关系

-   **设计器/预览**：画布内组件通过 **@local/runtime**、**vue-router / vue-i18n 别名** 等使用兼容层；仅在设计器环境中存在。
-   **出码**：生成的是主工程代码，引用主工程组件与真实依赖（如 `@/stores`、`vue-router`、`vue-i18n`），**不会**生成对 `@local/runtime` 或设计器桩的引用。
-   因此：兼容层只服务于「画布能看、能拖、能配」，不参与出码结果。

### 9.6 物料构建注意（pinia / 裸模块）

-   画布运行在 **iframe（srcdoc）** 中，通常**没有** import map 解析裸模块名（如 `"pinia"`）。
-   若在主工程 **vite.lowcode-materials.config.ts** 里把 **pinia** 设为 **external**，画布加载依赖 pinia 的物料脚本时会报 `Failed to resolve module specifier "pinia"`，导致该物料及后续依赖链加载失败。
-   **当前做法**：物料构建**不**将 **pinia** 设为 external，依赖 pinia 的物料（如使用 `@local/runtime` 里 store 的 mp-account-item、mp-account-picker）会将 pinia 打进自身 bundle，画布即可正常加载。仅 **vue** 与 **@local/mr-components** 保持 external，由画布/引擎侧提供。

### 9.7 复杂组件画布桩：全部使用源码样式、可批量维护

**问题**：画布桩若手写一套样式，与真实组件不一致且难以维护，还会**误导开发者**（拖拽后以为组件就长这样）。成百个复杂组件时无法逐个手改。

**做法**：画布桩的**模板与类名全部来自真实组件源码**，仅将复杂子组件（如弹窗、选择器）替换为占位 div，样式由**与源码一致的类名** + **一份共享的 design token CSS** 提供，桩的 script 只提供 stub 数据（store、$t、$currency 等），不引入真实子组件，保证画布可加载、可看、可维护。

**主工程脚本**（推荐）：

-   在主工程 **lowcode-materials/scripts/generate-canvas-stub.cjs** 中，从真实组件 `.vue` **提取完整 template**（正确处理嵌套 `<template>`），按配置将指定标签替换为占位 div（如 `mp-input` → 提取 `#input` 槽内容并包一层 `.mp-input-stub`，`mr-skeleton-text` → `.mr-skeleton-text-stub`，`mp-account-picker` → `.mp-account-picker-stub`），输出画布桩 `.vue`。
-   桩的 **script** 由脚本或人工维护：仅 defineProps + stub 数据（paymentStore、maskBalance、selectedAccount、$t、$currency 等），无 store/router 真实逻辑。
-   **样式**：与源码一致的类名（`text-h6`、`color-text-primary`、`min-h-42px` 等）由主工程 **canvas-stubs/shared-stub.css** 或画布侧设计系统提供；桩内只需少量占位类（如 `.mr-skeleton-text-stub`）的 scoped 样式。

**成百个组件时**：

-   在脚本的 **STUB_CONFIG** 中为每个复杂组件加一条（source、stubPath、replaceTags、props 或 scriptGenerator、可选 stubLabel），执行 `node lowcode-materials/scripts/generate-canvas-stub.cjs`（无参数则批量生成已配置组件），即可从源码生成/更新所有画布桩。**成百个组件时只维护 STUB_CONFIG，不手写 xxx-canvas.vue**；模板从源码提取并替换子组件为占位，script 可用通用桩（defineProps + $t/$currency/PaymentTool 等 stub）或按组件写 scriptGenerator。
-   真实组件**模板或类名变更**后，重跑一次脚本即可同步桩，**无需手改每个桩的样式**，维护成本可控。

**画布桩必做**：

-   **属性面板生效**：画布通过 `schema.props` 把属性面板的值传给组件，桩必须用 **defineProps** 声明与物料 schema 一致的字段（如 `label`、`placeholder`、`sceneType`、`pickerTitle`），并在模板中使用（如 `{{ label }}`、`{{ placeholder }}`），否则改左侧属性无效果。设计器传入的 `className` 会以 `class` 形式挂在根节点，桩根元素可写 `:class="$attrs.class"` 透传。
-   **未传 props 时也要能渲染**：画布初次拖入组件时往往**未传**复杂 props（如 `account`）。若模板直接写 `account.paymentTool`、`account.payerAccountNumber!.slice(-4)` 等，会因 `account` 为 undefined 抛错，导致**整块不渲染**（现象与「什么都不显示」一致）。桩的 script 必须为这类 prop 提供**安全默认值**：例如用 `const props = defineProps<...>();` 与 `const account = computed(() => props.account ?? DEFAULT_ACCOUNT)`，让模板始终拿到合法对象；`generateGenericStubScript` 已对含 `account` 的 props 自动注入 `DEFAULT_ACCOUNT` 与 `computed`，其它对象型 prop 若模板强依赖也可在 STUB_CONFIG 或 scriptGenerator 中同样处理。
-   **画布不显示 i18n key**：桩里若用 `const $t = (key) => key`，画布会直接显示 `common.availableBalance` 等 key，观感差。主工程在 **canvas-stubs/vue-i18n.ts** 维护 **FALLBACK**（key → 展示文案，与主工程 src/i18n 对齐），并导出 `t(key)`；生成脚本让画布桩 `import { t as $t } from '../vue-i18n'`，这样画布上显示「Available balance」等正常文案。新增物料若用到新的 i18n key，在 FALLBACK 中补一条即可。
-   **默认值英文优先**：桩内所有展示用默认值（如 DEFAULT_ACCOUNT.nickName、STUB_ACCOUNT.nickName、占位文案）统一使用英文（如 "Account Item"、"Select Payment Method"），避免画布上出现中文占位。
-   **为何真实组件难在画布展示**：除 store/utils/i18n 等运行环境外，**子组件未就绪**也会导致失败。例如 MpAccountInput 由 **mp-input**、**mr-skeleton-text**、**mp-account-picker** 等组合而成，画布渲染时 Vue 需能解析这些标签；若画布内未注册或未加载这些子组件，会报错或空白。要用真实组件获得真实样子，需保证画布能解析全部子组件（如 mr-\* 由设计器预加载的 mr-components 提供，mp-input/mp-account-picker 等需在同一物料包或画布内注册），且运行环境（store/i18n/router 桩）一致。

### 9.8 MpAccountInput 依赖与分步接入顺序（按主工程源码）

**源码结论**（以主工程 `src/components/account/` 为准）：

-   **MpAccountInput** 直接使用：`mp-input`、`mp-account-picker`，以及 mp-input 槽内的 `mr-skeleton-text`。其中 mp-input 已在设计器可拖拽使用，无需从它起步。
-   **mp-account-picker** 使用：`mp-popup`、`mr-segment`、`mr-segment-button`、`mr-label`、`mp-account-item`、`mr-divider`、`mp-empty`；script 依赖 `useI18n`、`useRoute`、`usePaymentStore`。
-   **mp-account-item** 使用：`mp-cell`、`mp-icon`；script 依赖 `usePaymentStore`、`useAccountStore`、`$t`、`$currency`、`$getCurrencySymbol`。

**mp-account-item 是否导入成功会直接影响 MpAccountInput**：画布渲染 MpAccountInput 时会加载 mp-account-picker，picker 内用 `v-for` 渲染多个 `<mp-account-item>`；若 mp-account-item 未在画布注册或无法解析，Vue 无法解析该标签，列表不渲染或报错，MpAccountInput 表现异常。因此必须先保证 mp-account-item 在设计器画布可加载、可渲染。

**推荐分步顺序（先打地基再上组合组件）**：

1. **第一层**：**mp-account-item**。依赖 mp-cell、mp-icon（主工程 manifest 中已有），以及 store/全局方法桩、`PaymentTool`（来自 `@/utils`）。主工程已做：`canvas-stubs/utils.ts` 导出 `PaymentTool` 枚举，物料构建 alias `@/utils` 指向该桩；manifest 中 MpAccountItem 暂设 `hiddenInPanel: false` 便于拖拽验证。**验证**：主工程执行 `pnpm run build:designer-materials`，设计器配置主工程 bundle URL，在物料面板找到「账户项」拖到画布，确认能渲染且属性（如 account JSON、selected）生效；通过后可把 `hiddenInPanel` 改回 `true`。
2. **第二层**：**mp-account-picker**。主工程已做：用 generate-canvas-stub.cjs 生成 **mp-account-picker-canvas.vue**（replaceTagOnly 保留 mp-popup 壳为 div、子组件替为占位），入口 **mp-account-picker.js** 导出该桩。**注意**：入口为画布桩单 vue 时不要放入 `vite.lowcode-materials.config.ts` 的 `INLINE_ENTRIES`，否则内联插件改写 `export { default as X }` 易触发 `SyntaxError: Unexpected identifier 'as'`；不内联时入口与 chunk 同目录部署即可正常加载。
3. **第三层**：**MpAccountInput**。主工程已做：**mp-account-input-canvas.vue 由 generate-canvas-stub.cjs 从真实组件源码生成**，与真实组件结构、类名、分支（loading/selectedAccount/placeholder）一致，仅将 mp-input、mp-account-picker、mr-skeleton-text 替为占位，并补 label 行；避免手写桩与源码差距大、误导开发者。入口导出该桩，$t 用 vue-i18n，不内联。验证：拖拽到画布应看到与真实组件一致的 label + 内容区布局。

## 十、主工程物料包 vs 设计器本地物料：为何主工程生成包后问题多

本节说明「设计器本地导入并已调试好的组件」与「主工程生成物料包让设计器加载」的**本质差异**，以及为何后者会重新暴露出加载错误、宽度、国际化等问题；并给出**过渡方案**与**目标方案**，便于在「不重复踩坑」的前提下逐步切换到主工程物料包。

### 10.1 设计器本地导入时为何能一次调通

在设计器内按 [导入组件标准操作步骤](#导入组件标准操作步骤推荐) 做的流程是：

| 环节           | 设计器本地做法                                                                                                                                               | 结果                                                      |
| -------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------ | --------------------------------------------------------- |
| **源码**       | 放在 **designer-demo/materials-src/**，与主工程**拷贝/同步**后在设计器侧维护                                                                                 | 同一份组件源码                                            |
| **构建**       | 主工程 **vite.lowcode-materials.config.ts** 构建，**alias** 将 `@local/runtime`、`vue-router`、`vue-i18n` 等指向主工程 **lowcode-materials/runtime/** 下的桩 | 产出的 JS 里已是**画布可用的桩**，无主工程真实 store/i18n |
| **样式**       | 构建产出 **style.css** 在设计器 public，画布与设计器同源加载                                                                                                 | 宽度、主题与设计器一致                                    |
| **物料列表**   | `/mock/bundle.json` + `/mock/business-materials.json`，script 为相对路径，设计器在插件环境下会转为设计器 origin 的绝对 URL                                   | 无 CORS、无 404                                           |
| **区块接口**   | `/material-center/api/block` 走设计器 mock 或本地逻辑，与当前物料列表一致                                                                                    | 拖拽即能解析 block，无 Empty response                     |
| **画布运行时** | 画布 Vue 应用已执行 **installRuntimeCompat(app)**，提供 $t、Pinia 桩等                                                                                       | 组件内用的 store/i18n 与桩一致，国际化、展示正常          |

因此：**同一套组件**在设计器里构建、同一套 runtime、同一套 mock/block、同一套样式，所以「调一次就好」，不会出现主工程包加载后的各种问题。

### 10.2 主工程生成物料包后为何问题多

当改为「主工程构建 → dist/lowcode-materials → 设计器通过 URL 加载 bundle」时，下列环节与设计器本地**不一致**：

| 环节          | 主工程物料包现状                                                                                                                                                                  | 导致的现象                                                                                               |
| ------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------- |
| **构建环境**  | 主工程 **vite.lowcode-materials.config.ts** 未把 store、vue-i18n、vue-router 指到**桩**，组件打进去的是主工程真实依赖或未注入的全局                                               | 画布内无主工程真实 store/i18n 环境 → **国际化错、行为错**；部分 chunk 用 Node(Buffer/crypto) 需 polyfill |
| **样式**      | 主工程产出 **mr-bank.css**，画布从 localhost:3000 拉；画布根字体/变量若与设计器不一致                                                                                             | **宽度、布局**与在设计器本地时不一致                                                                     |
| **物料/区块** | bundle 从 `http://localhost:3000/bundle.json` 拉，CORS、插件代理、block 解析顺序等需单独处理；block 请求若早于主工程 bundle 写入物料 store                                        | **Empty response、区块 xxx 加载错误**                                                                    |
| **运行时**    | 画布虽仍挂载了 designer 的 **installRuntimeCompat**，但主工程产出的 JS 里若直接 `import { useI18n } from 'vue-i18n'` 等，用的是**自带/打包进去**的 vue-i18n，不是设计器挂的 $t/桩 | 文案、多语言仍不对                                                                                       |

所以：**不是「主工程生成物料包」这件事本身难，而是主工程当前产出的 JS 是为「真实应用」构建的，缺少设计器画布所需的桩与一致样式**；之前在设计器本地已经通过「设计器构建 + runtime 别名」把这些问题都规避掉了。

### 10.3 过渡方案：继续用设计器本地物料（稳定可用）

若近期目标是**先保证画布稳定、不重复调试**，建议：

-   **继续使用设计器本地物料**：`engine.config.material` 只保留设计器自有的 bundle（如 `["/mock/bundle.json", "/mock/business-materials.json"]`），**不要**加入 `http://localhost:3000/bundle.json`。
-   **主工程只做两件事**：  
    1）作为**源码与 schema 的源头**（组件实现、物料 manifest 可从主工程同步到设计器 materials-src / materials-manifest）；  
    2）**出码**生成主工程代码，引用主工程真实依赖。
-   **设计器**：仍按 [导入组件标准操作步骤](#导入组件标准操作步骤推荐) 在 **materials-src** 维护/同步组件，用 **build:materials** 产出 `public/mock/materials/`，配合现有 runtime、block、样式，**无需再踩一遍加载/宽度/i18n 的坑**。

这样「主工程生成物料包」仅作为后续目标，当前画布体验与之前已调好的设计器本地导入一致。

### 10.4 目标方案：主工程产出「画布可用」的物料包

若要坚持「设计器只加载主工程生成的物料包、不再在设计器里维护 materials-src 构建」，则需让**主工程构建产物**在画布中的行为与「设计器本地构建 + runtime」一致：

1. **主工程增加「设计器画布」构建模式**  
   在 **vite.lowcode-materials.config.ts**（或独立 config）中：

    - 将 **vue-router**、**vue-i18n**、主工程用到的 **store 入口**（如 `@/stores/account` 等）**alias 到与设计器同签名的桩**。
    - 桩来源：本仓库不发布 packages 到公网，主工程需从 **designer-demo/src/runtime** 复制或链接到主工程，在物料构建中 alias 到该桩（详见 12.3.2）。
    - 保证业务组件里 `useI18n()`、`useRoute()`、`useAccountStore()` 等打到**物料包**产物里的是**桩实现**，这样在设计器画布内与设计器挂载的 `installRuntimeCompat` 一致，国际化、store 行为正常。

2. **样式与根布局**

    - 主工程产出的 **mr-bank.css** 若依赖根字体或 CSS 变量，需在设计器画布内能加载且与设计器根样式兼容；必要时在设计器画布容器内注入与主工程一致的根变量或 class，避免宽度/布局偏差。

3. **已做的与可保留的**
    - 当前已做的：CORS、bundle.json 直连、block 重试与返回格式、字体 CSP、Node polyfills 等，在主工程改为「画布模式」构建后**可继续沿用**；届时 block 从物料 store 解析、主工程 bundle 正常加载，即可减少 Empty response 与加载错误。

按上述方式，主工程生成的物料包在画布中的表现可对齐「设计器本地导入并已调试好的」效果，无需再从头排查一遍加载、宽度、国际化问题；文档 [七、复杂组件导入与运行时兼容层](#七复杂组件导入与运行时兼容层) 中的桩与 alias 思路可直接复用到主工程的设计器构建配置中。

### 10.5 不采用过渡方案时的路径：设计器独立部署 + 动态多物料包

目标：设计器**独立部署**，通过配置（如多个 bundle URL）**动态加载多个物料包**，有新物料时只需发布新的 bundle 或新 URL，**无需重新编译/打包设计器**。

这与「过渡方案」不冲突，而是**同一条路线**的两种用法：

-   **过渡方案**：短期先只用设计器本地 bundle，保证稳定。
-   **目标方案**：设计器只连「符合画布协议的 bundle URL」，一个或多个，全部动态加载。

设计器侧只需保证：

1. **物料源可配置**：`engine.config.material` 或等价配置支持多个 URL（含主工程、其他业务的 bundle）。
2. **block 从本地解析**：当某个 bundle 没有对应的服务端 block 接口时，设计器用 **getBlockFromMaterialStore** 从已加载物料中按 label 解析 block，避免 404 / Empty response（见下节快速修复）。
3. **画布运行时统一**：画布内挂载 **installRuntimeCompat**，提供 $t、Pinia 桩等；**谁产出物料包，谁负责**在构建时使用与画布兼容的桩或适配层（见 10.6），设计器不依赖具体业务工程。

这样「设计器与主工程解耦」：设计器只依赖「物料协议 + 画布运行时约定」，不依赖主工程仓库或构建产物；主工程（或任何一方）只要产出符合协议的 bundle，即可被设计器动态加载。

### 10.6 「画布构建模式」的含义、与设计器解耦、对维护的影响

**「主工程增加设计器画布构建模式」** 指的是：**谁产出给设计器用的物料包，谁在构建时**把 vue-router、vue-i18n、store 等 **alias 到与画布同签名的桩**，使产出的 JS 在画布内能直接用设计器挂好的 $t、Pinia 等，而不是「设计器去适配主工程」。

要点：

-   **设计器保持独立**：设计器只提供**约定**（画布里有哪些全局能力、桩的接口长什么样），不强制依赖主工程代码。主工程（或其它业务）只是「物料包生产者」之一。
-   **桩的来源**：本仓库为 TinyEngine 官网源码，packages 不发布到公网；主工程需从 **designer-demo/src/runtime** 复制或链接到主工程，在「物料构建」时做 alias，无需、也无法通过 npm 安装画布桩包。
-   **对后续维护的影响**：
    -   设计器：只维护「画布运行时约定」和该约定包，与具体业务工程无直接依赖。
    -   主工程（或其它业务）：在「为设计器产出物料」的构建脚本里多一条构建模式（如 `build:designer-materials`），alias 指向约定包；主工程日常业务构建不受影响，独立运行也不受影响。
    -   新物料：发布新 bundle 或新 URL 即可，设计器无需重新编译。

因此「画布构建模式」**不会**把设计器与主工程绑死，而是把「画布兼容」的责任放在**物料包生产者**一侧，设计器只消费符合协议的 bundle。

### 10.7 可快速落地的修复项（加载失败、宽度、国际化）

在向「目标方案」推进时，可先做以下修复，参考设计器本地已调通的经验，减少重复踩坑。

| 问题                                        | 可能原因                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               | 修复思路                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| ------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **区块加载错误 / Empty response**           | 1）拖拽时 block 请求早于物料 merge 完成；2）主工程 bundle 返回结构不是 `materials` 或 `data.materials`，或 `components[].component` 缺失，导致 getBlockFromMaterialStore 查不到                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                        | 1）设计器侧：对 `/material-center/api/block` 在 getBlockFromMaterialStore 为空时**多次重试**（如 400ms、800ms），并兼容 label 大小写（首字母大写）；加载远程 bundle 时会校验 `materials.components` 及每项 **component** 字段，异常时控制台打 warning。2）主工程 bundle：保证 bundle.json 含 `materials.components`，且每项有 **component** 字段（组件名，如 MpAccountInput），与面板/区块使用的 label 一致；可在生成 bundle 后执行 **`pnpm run validate:bundle-structure -- <bundle 路径或 URL>`**（见 designer-demo/scripts/validate-bundle-structure.cjs）做自检。 |

| **国际化不对**                              | 主工程物料 JS 自带 vue-i18n 或真实 i18n，与画布挂的 $t/桩不一致                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                        | 主工程「画布构建」时把 vue-i18n、store 等 alias 到约定桩；或物料不打包 vue-i18n，使用画布注入的全局 $t（designer 已挂 installRuntimeCompat）。                                                                                                                                                                                                                                                                                                                                                                                                                        |

**设计器侧已做的**：block 从物料 store 解析、400ms/800ms/1200ms 多次重试、label 首字母大写兼容、CORS 与 CSP、Node polyfills。**Materials 日志**：设计器加载时会打 `[Materials] 开始拉取物料，bundle 数量: N` 和每条 `[Materials] 已加载物料 bundle: <url>, 组件数: X`（本地与远程 bundle 都会打）；控制台过滤 **Materials** 即可看到。若某 block 在 store 中未找到会打 `[Materials] block 未在已加载物料中找到: label=XXX，将走插件代理...`。**远程 bundle 校验**：加载主工程（或任意远程）bundle 时，若 `materials.components` 缺失或某组件缺少 **component** 字段，控制台会打 warning。若主工程 bundle 结构正确且组件名与 label 一致，多数「加载错误」可消除；再配合主工程侧在物料构建时把 store/i18n/router alias 到与画布同签名的桩（桩从 designer-demo/src/runtime 复制，见 12.3.2）与样式约定，宽度与国际化会趋同设计器本地效果。

**远程 bundle 按需加载（designer-demo）**：来自**远程 URL** 的物料包（如主工程 `http://localhost:3000/bundle.json`），其组件脚本**不再加入画布预加载列表**（`parseMaterialsDependencies(..., { skipScriptPreload: true })`），仅在用户**拖拽该组件时**再请求对应 script URL 并注册。这样同一 bundle 里某个脚本报错（如语法错误、缓存旧版）不会导致其他组件（如 MpAccountItem）也无法加载；本地/内置物料仍预加载，行为不变。

## 十一、目标架构与标准化物料生产流程（当前方向）

### 11.1 文档定位说明

-   **第一～九章**：描述的是**旧流程**（主工程源码拷贝到设计器 `materials-src`，在设计器内构建并导入）。该流程仅作参考，设计器内的 `materials-src`、`mock/materials` 及对应产出物**将来会移除**，一切以主工程产出的物料包为准。
-   **第十章**：分析「主工程产包 + 设计器加载」时遇到的问题与目标方案（画布构建模式、设计器独立、动态多 bundle）。
-   **本章及第十二章**：明确**目标架构**与**实施计划**，形成可复用的标准化流程，供多项目使用。

### 11.2 目标架构

| 角色                           | 职责                                                                                                                                                                                                                                                                                                                      |
| ------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **主工程（多个业务项目均可）** | 在主工程内通过命令/脚本执行「画布模式」构建，产出符合协议的物料包（bundle 元数据 JSON + 编译后的 ESM/CSS）；产物可放在本地目录或发布到 npm 私服。构建时需将 store、vue-i18n、vue-router 等 alias 到与画布同签名的桩（桩从 designer-demo/src/runtime 复制，见 12.3.2），保证产出的 JS 在设计器画布内行为与设计器约定一致。 |
| **设计器**                     | **独立部署运行**，不依赖任何主工程源码。通过 `engine.config.material` 及运行时注入的物料包 URL（如 `window.TINY_MATERIAL_BUNDLE_URLS`）拉取一个或多个 bundle，按协议解析并展示；画布内挂载统一的运行时兼容层（如 `installRuntimeCompat`）。                                                                               |
| **VS Code 插件（可选）**       | 打开设计器时，将「物料包地址」传给设计器（本地 serve 的 URL 或 npm 私服 URL）；设计器根据地址拉取并合并物料，实现多项目、多物料源的低代码开发。                                                                                                                                                                           |

### 11.3 标准化原则

-   **不盲目打补丁**：为实现某一效果而到处补漏、忽略整体架构的修改应避免；改动需符合「设计器只消费协议 + 主工程只产画布可用包」的边界。
-   **以主工程产出为准**：设计器内现有的本地物料（`materials-src`、`mock/materials`、`business-materials.json` 等）仅作**参考与过渡**，最终都会收敛到「由各主工程构建并暴露 URL，设计器动态加载」。
-   **多项目复用**：同一套设计器可接入多个主工程产出的物料包；主工程只需遵循「画布构建模式 + 物料资产包协议」，无需改设计器代码。

### 11.4 当前设计器本地物料的定位

-   `designer-demo/materials-src`、`mock/materials`、`mock/bundle.json`、`mock/business-materials.json` 等用于**开发期参考**和**过渡期内置物料**。
-   后续将逐步去掉上述本地组件源码与产出物，仅保留设计器运行时所必需的**内置基础物料**（若有）；业务/原子组件一律由主工程产出的 bundle URL 提供。

### 11.5 「设计时兼容版组件」路线（以 MpInput 为例）

> 旧思路回顾：尝试直接把主工程真实组件（例如基于 `ion-input` 的 MpInput）打包进物料，让画布渲染同一份组件。实践发现，这类**强依赖 Wise Core DOM + 全局 CSS 的基础控件**在 Tiny 画布 iframe 中很难 95% 还原：要么必须引入整套 Wise Core 主题（破坏画布布局），要么样式严重走样（变成带边框的小 input），调到 70–80 分都很吃力。

为解决「**画布要尽量接近真实效果，但又不想把 Wise Core 整套搬进设计器**」的矛盾，对这类基础控件采用**设计时兼容版组件（design-time compatible component）**路线：

-   **定义**：

    -   **运行时组件**：主工程真实组件，用于实际页面和出码（例如 `src/components/base/mp-input.vue`，内部用 `ion-input`、依赖 Wise Core 主题）。
    -   **设计时兼容版组件**：仅供设计器画布使用的实现，结构/样式贴近设计器本地 mock 版，**不依赖 Wise Core DOM**，只依赖 `@local/mr-components`、`mr-bank.css` 等画布友好的依赖。

-   **适用场景**：

    -   基础控件（输入框、按钮、标题栏等）在主工程中严重依赖 Wise Core/Ionic 的特殊 DOM 与全局 CSS；
    -   这类控件在设计器本地 mock（`designer-demo/materials-src` 内）已经有一套成熟、适配 Tiny 画布的实现（例如本地 MpInput mock 只包一层 `MrField`，靠 Vant + 自己的样式就能渲染出下划线输入框）。

-   **主工程侧约定（以 MpInput 为例，目录建议）**：

    -   新建目录：`mobilebanking/lowcode-materials/design-components/mp-input-designer.vue`
        -   模板与逻辑参考 **设计器本地 mock 的 MpInput**（`designer-demo/materials-src/mp-input/mp-input.vue`）：
            -   使用 `MrField` / `@local/mr-components`，而**不使用 `ion-input`**；
            -   props 尽量与运行时 MpInput 保持一致（`label` / `labelAlign` / `placeholder` / `type` / `inputAlign` / `readonly` / `disabled` / `errorMessage` / `maxlength` 等）；
            -   样式依赖 `mr-bank.css` 已有变量（`--mr-color-text-primary`、`--mr-color-text-placeholder` 等），只做少量必要的补充（如 `.mp-input :deep(.van-field__body input)`）。
    -   为设计时组件增加入口：`lowcode-materials/entries/mp-input-designer.js`：
        ```js
        import MpInputDesigner from '../design-components/mp-input-designer.vue';
        export { MpInputDesigner as MpInput };
        ```
        这样画布端 `component: "MpInput"` 仍然拿到一个名为 `MpInput` 的导出，但实现是**设计时兼容版**。

-   **物料清单与出码映射**：

    -   在 `lowcode-materials/manifest.json` 中，仍然以 **业务语义组件** 的视角维护：
        ```json
        {
            "component": "MpInput",
            "group": "业务组件",
            "nameZh": "输入框",
            "nameEn": "Input",
            "icon": "component-default",
            "script": "mp-input-designer.js", // 画布加载设计时版
            "exportName": "MpInput",
            "package": "@local/mp-input",
            "hasCss": true,
            "description": "业务组件 mp-input，单行输入"
        }
        ```
    -   **画布侧**：通过 `npm.script = mp-input-designer.js` 加载设计时兼容版组件，保证拖拽效果与设计器本地 mock 一致（只有下划线、对齐正确）。
    -   **出码侧（约定）**：出码引擎根据 `package: "@local/mp-input"` / 额外的 runtime 配置，将 schema 中的 `MpInput` **映射回主工程真实组件**（例如生成 `import MpInput from '@/components/base/mp-input.vue'`），实现「画布看兼容版、运行用真实版」。

-   **优缺点权衡**：

    -   **优点**：
        -   画布效果可做到接近或等同于当前设计器本地 mock 的 95 分视觉；
        -   不需要在 Tiny 画布中引入 Wise Core / Ionic App 级别的 CSS 与 DOM 结构；
        -   主工程仍然是物料的唯一生产者（设计器不再保存 mock 源码），多项目可复用同一套路径。
    -   **限制**：
        -   运行时组件与设计时组件在实现上不是同一份代码，**需要在主工程内有一份「设计时兼容实现」**；
        -   兼容版应尽量只做展示与基础交互，不承载复杂业务逻辑，避免两边逻辑不一致。

-   **推广策略**：
    -   先从 **MpInput 这类基础控件** 做 POC：主工程产出设计时 MpInput → 设计器加载 `mp-input-designer.js` → 对比画布与真实页面效果；
    -   经验成熟后，再为 **MpAccountItem / MpAccountPicker / MpAccountInput** 这类复杂业务组件设计各自的设计时兼容版（结合 [9.7 画布桩生成] 的脚本思路），逐步替换当前手写桩或难以维护的方案。

#### 12.3.2 为什么主工程物料构建需要桩，以及桩从哪里来

**为何需要桩（澄清「本末」）**  
主工程跑自己的应用时，用真实 store、utils、router、i18n 即可，**不需要**也**不应该**用设计器的桩。  
需要桩的只有一件事：**主工程为设计器产出「物料包」的那次构建**。产出的 JS 会被设计器加载到**设计器的画布**里执行；画布环境是设计器的 iframe，没有主工程的 store/utils/router。若这份 JS 里引用的是主工程真实 store 等，在设计器画布里会报错或行为异常。因此**物料构建**（仅此一次构建）时，须把 store/router/i18n 等 alias 成与设计器画布 `installRuntimeCompat` **同签名**的桩，这样产出的 JS 在设计器画布里才能正常跑。桩只是「物料构建时的替换目标」，不是给主工程日常运行用的。

**桩从哪里来**  
本仓库不发布 `packages` 到公网（仅官网源码），主工程无法通过 npm 安装画布桩包。可选两种方式：（1）从本仓库**复制或链接 designer-demo 的 `src/runtime`** 到主工程，在物料构建的 Vite 里把 store/router/i18n 等 alias 到该目录；（2）**主工程在仓库内自建桩目录**（如 `lowcode-materials/canvas-stubs/`），与 designer-demo 的 `src/runtime` 对齐 **store id** 与 API 签名（如 `common.account`、`common.payment`），在物料构建中把 `@/stores` alias 到该目录，并将 `pinia` 设为 non-external，使桩与 pinia 一并打入物料，画布内与设计器挂载的 Pinia 同 id 即可共用。设计器画布已通过 `installRuntimeCompat(app)` 提供 `$t`、`$currency`、`$fd` 等全局方法；主工程物料构建只需保证产出的 JS 引用的是同签名桩。

**MpAccountInput / MpAccountPicker 依赖与桩对应（主工程 canvas-stubs 已覆盖）**

| 依赖                                     | 用途                                                                                          | 桩位置                         |
| ---------------------------------------- | --------------------------------------------------------------------------------------------- | ------------------------------ |
| `@/stores` → usePaymentStore             | paymentWayLoading、getPaymentWay、getDefaultPaymentWay、queryPaymentWay、calcPaymentWayAmount | canvas-stubs/stores/payment.ts |
| `@/stores` → useAccountStore             | maskBalance                                                                                   | canvas-stubs/stores/account.ts |

#### 12.3.3 可立即验证（无需真实主工程仓库联调）

在主工程尚未准备好 `lowcode-materials` 构建脚本之前，可以使用任意一个符合物料协议的 bundle.json 作为「示例物料包」，只需将其通过静态服务暴露为 URL，并在环境变量或 VSCode 配置中填写该 URL。推荐用 **env 或 getInitData** 传 URL，与插件交互方式一致，避免依赖地址栏拼接。

**方式 A：环境变量**

1. 在 `env/.env.local` 或 `env/.env.development` 中增加一行：
    ```bash
    VITE_MATERIAL_BUNDLE_URLS=http://localhost:3000/bundle.json
    ```
2. 启动设计器：`pnpm run dev`，浏览器打开 `http://localhost:8090`（无需带 `?materialBundle=...`）。
3. **预期**：物料面板出现示例 bundle 中声明的组件分组和组件，可拖入画布并正常渲染（若脚本本身无错误）。

**方式 B：URL 参数**

1. 起一个静态服务（如 `npx serve dist/lowcode-materials -p 3000`），确保 `http://localhost:3000/bundle.json` 可访问。
2. 启动设计器：`pnpm run dev`，浏览器打开 `http://localhost:8090/?materialBundle=http://localhost:3000/bundle.json`。
3. 预期同上；若 3000 未开或跨域被拦，会看不到效果。

**方式 C：插件 getInitData**  
插件在 `getInitData` 的 result 中返回 `materialBundleUrls: ['http://...']`，设计器会合并并刷新物料（见 `docs/VSCode-Integration.md`）。
