# 业务组件与原子组件导入设计器方案

> **新增业务组件时**：先看上方 **[导入组件标准操作步骤](#导入组件标准操作步骤推荐)**，按表格步骤执行；需详细示例时再跳至 **[七、新增业务组件实操步骤](#七新增业务组件实操步骤以-mp-progress-为例)**。
>
> **导入组件必守规则**：① **图标**：物料需配置 `icon` 或使用默认图标（见 [4.7.1](#471-图标)）；② **国际化**：分类用 `group: "原子组件"` / `"业务组件"`，面板英文下显示为 MR Components / MP Components；③ **名称**：`name` 必须含 `zh_CN` 与 `en_US`，保证面板与画布中英文一致（见 [4.7](#47-导入组件的图标与国际化规则必遵守)）。

## 导入组件标准操作步骤（推荐）

**以后凡要导入新组件，按下面顺序做即可。** 详细说明与示例见第七章、第八章。

### 业务组件（mp-xxx）

| 步骤 | 操作 | 说明 |
|------|------|------|
| 1 | 在 **materials-src/** 下新建目录（如 `mp-xxx`），放入 `index.js` 与组件 `.vue` 文件 | 组件若依赖原子组件，从 `@local/mr-components` 引入；**构建时会自动扫描该目录生成 entry，无需改 vite 配置**；详见 [7.1](#71-把源码放到-materials-src) |
| 2 | 在 **mock/materials-manifest.json** 的 `components` 中追加一条 | 填 `component`、`group`、`nameZh`、`nameEn`、`icon`、`script`（如 `mp-xxx.js`）、`exportName`、`package`、`hasCss`；需自定义属性面板时加 `schemaExtra`；详见 [8.4](#84-物料清单-自动生成与校验推荐) |
| 3 | 执行 **`pnpm run generate:materials-json`** | 根据清单生成符合协议的 `business-materials.json` |
| 4 | 执行 **`pnpm run build:materials`** | 构建物料脚本（会扫描 materials-src 自动包含新组件），产出到 `public/mock/materials/` |
| 5 | （可选）执行 **`pnpm run validate:materials-json`** | 校验 `business-materials.json` 必填字段 |
| 6 | 运行 **`pnpm run dev`**，在物料面板拖拽新组件到画布验证 | 若在 VSCode 插件中使用，同样拖拽验证；详见 [7.5](#75-验证) |

### 原子组件（mr-xxx）

| 步骤 | 操作 | 说明 |
|------|------|------|
| 1 | 在 **materials-src/mr-components.js** 中从 Vant/Ionic 引入并 re-export | 如 `export { Progress as MrProgress }`；详见 [4.1](#41-设计器侧提供统一-mr-原子组件入口与样式) |
| 2 | 在 **mock/materials-manifest.json** 的 `components` 中追加一条 | `script` 填 `mr-components.js`，`package` 填 `@local/mr-components`，`hasCss` 一般为 `false` |
| 3 | 同业务组件步骤 3～6 | 执行 generate → build:materials →（可选）validate → 浏览器/插件中拖拽验证 |

### 小结

- **源码**：只维护 **materials-src/**（构建时会**自动扫描**该目录生成 entry，无需改 vite.materials.config.ts）。
- **协议 JSON**：只维护 **materials-manifest.json**，用 **`pnpm run generate:materials-json`** 生成 `business-materials.json`，无需手写协议字段。
- **构建**：**`pnpm run build:materials`** 生成 `public/mock/materials/`，该目录勿手改。

### 1.1 目的

本文档总结将**业务组件（mp 开头）**与**原子组件（mr 开头）**导入 TinyEngine 设计器（designer-demo）的可行性、推荐方案与实施流程，供后续具体落地与开发参考。

### 1.2 背景

- **业务组件**：如 `mp-card`，位于业务项目（如 mobilebanking）`src/components` 下，以源码形式维护，未发布为 npm 包。
- **原子组件**：如 `mr-divider`，通过 resolver 将 **Vant**、**Ionic** 等库的组件映射为 mr 前缀命名，在业务组件中被广泛引用。
- **需求**：
  - 在设计器中可拖拽使用业务组件（mp-*）。
  - 在设计器中可拖拽使用原子组件（mr-*）。
  - 业务组件内部对原子组件的依赖在设计器画布与预览中能正确解析并渲染。
  - 方案尽量简单、不繁琐，便于持续接入新组件。

## 二、可行性结论摘要

### 2.1 物料资产包与「npm」的含义

- 设计器通过 `engine.config.material` 配置的 bundle（如 `/mock/bundle.json`）加载物料；支持**多个物料源**（数组）。
- 协议中的 **npm** 字段表示「组件来源的元数据」（包名、脚本地址、导出名等），**不要求**组件一定从 npm 仓库安装。
- 画布通过 `npm.script` 的 URL 动态 `import(script)` 加载组件；**script 可为任意可访问的 ESM 地址**（含本地路径），不限于 CDN。

因此：**用源码构建出的 ESM + 在 bundle 中正确配置 npm（含 script、exportName 等），即可在设计器中使用，无需发布 npm 包。**

### 2.2 业务组件（源码形态）接入

- **可行**：将业务组件（如 mp-card）构建为 ESM（如 `mp-card.js`），部署到设计器可访问的路径，在物料包中为该组件配置一条记录，`npm.script` 指向该 ESM，`npm.package` 使用占位符（如 `@local/mp-card`）。
- **bundle 配置**：每个要在设计器中使用的组件，都必须在物料包的 `components` 与 `snippets` 中各有一条对应配置；可沿用现有「单组件 JSON + buildMaterials 合并」机制，便于批量维护。

### 2.3 原子组件（Vant / Ionic）在设计器中的必要性

- 业务组件内部会引用原子组件（如 mp-card 使用 mr-divider）；若设计器环境**不提供**这些依赖，加载业务组件时会报错或无法渲染。
- 同时，若希望原子组件也能在设计器中**单独拖拽使用**，设计器必须提供其实现（Vant / Ionic 或统一封装）。
- **原子组件来源**：mr-* 既有来自 **Vant**（如 mr-divider），也有来自 **Ionic**，需统一考虑，避免设计器侧配置多套、重复且难以维护。

## 三、推荐方案：统一 mr 原子组件入口（Vant + Ionic）

### 3.1 思路

- **设计器只维护一份「原子组件」运行时**：一个 ESM，内部从 **Vant** 和 **Ionic** 按需引入组件，并以 **mr 命名**统一 re-export（与业务项目中的 resolver 命名一致）。
- **原子组件**：在物料中为每个 mr-* 配置一条，`npm.script` 均指向该统一入口，仅 `exportName` 不同。
- **业务组件**：构建时将这一份入口作为 **external**，不把 Vant/Ionic 打进业务组件 ESM；运行时由设计器提供的同一份脚本解析所有 mr-*。

这样实现：

- 设计器只需配置**一个**脚本 + Vant 与 Ionic 的样式，逻辑简单。
- 原子组件与业务组件共用同一套依赖，无重复、无两套来源。
- 后续新增第三方 UI 库时，只需在统一入口中增加 re-export，设计器配置可保持不变。

### 3.2 与「业务组件自包含」的对比

若采用「每个业务组件 ESM 内打包 Vant/Ionic」：

- 原子组件若要单独拖拽，设计器仍需再提供一份 Vant/Ionic（或 mr 入口）。
- 结果：设计器内存在两套 Vant 来源（一份给原子物料、一份被打进各业务组件），体积与维护成本都增加。

因此，在**原子组件也需导入设计器并拖拽使用**的前提下，推荐**不**采用业务组件自包含，而是采用**设计器统一提供一份 mr 入口，原子与业务组件共同复用**。

### 3.3 为何用「一个入口」同时接 Vant 和 Ionic

- 若设计器分别配置 Vant 和 Ionic：需维护两个库、两套样式，原子物料要按来源选择不同 script，业务组件构建也要 external 两个包，流程更复杂。
- 采用**一个 mr 入口（内部再接 Vant 和 Ionic）**：设计器只配置「一个脚本 + 两套样式」，原子与业务组件都只依赖这一入口，**简单、不繁琐**，且与「尽量简单」的目标一致。

## 四、方案流程与实施要点

### 4.1 设计器侧：提供统一 mr 原子组件入口与样式

1. **维护一个 ESM**（如 `mr-components.js`，名称可自定）：
   - 从 **Vant** 引入需要的组件，按 mr 命名 re-export（例：`export { Divider as MrDivider } from 'vant'`）。
   - 从 **Ionic** 引入需要的组件，同样按 mr 命名 re-export。
   - 与业务项目（mobilebanking）中 resolver 的映射保持一致（组件名、使用的具体子组件）。
2. **部署**：将该 ESM 部署到设计器/预览可访问的 URL（如 `designer-demo/public/mock/materials/mr-components.js`）。
3. **设计器加载方式**：通过 import map 或物料依赖配置，使画布能解析该入口（如配置为 `@your/mr-components` 或对应 URL）。
4. **样式**：在设计器/预览中加载 **Vant 样式** 与 **Ionic 样式**（可两个 link，或合并为一个），否则原子组件会缺样式。

### 4.2 原子组件：作为物料录入

1. 对每个需要在设计器中拖拽的 mr-*（如 mr-divider、mr-button 等），在物料包（主 bundle 或单独业务物料 JSON）中新增一条：
   - `component`：画布使用的组件名（如 `MrDivider`）。
   - `npm`：`package` 占位（如 `@local/mr-components`），`script` 指向上述统一入口 URL，`exportName` 与入口中的导出名一致（如 `MrDivider`）。
   - `schema`、`configure`、`snippets` 按需配置（可与现有 Tiny 组件类似结构）。
2. 所有原子组件物料共用**同一个** `npm.script`，仅 `exportName` 不同。

### 4.3 业务组件：构建与物料配置

1. **构建**：
   - 将业务组件（如 mp-card）构建为 ESM（如 `mp-card.js`），部署到设计器可访问路径（如 `designer-demo/public/mock/materials/mp-card.js`）。
   - 构建时把 **mr 原子组件入口**（或 Vant/Ionic）设为 **external**，不打包进业务组件；产物中对 mr-* 的 import 指向该统一入口（通过 alias/resolver 在构建时配置）。
2. **物料配置**：
   - 在物料包中为每个业务组件配置一条：`component`、`npm`（`package` 占位、`script` 指向该业务组件 ESM、`exportName` 等）、`schema`、`configure`、snippet 等。
   - 与现有「单组件 JSON + buildMaterials 合并」机制保持一致，便于批量维护与扩展。

### 4.4 物料源与 bundle 组织（可选）

- `engine.config.material` 支持数组，可配置多个物料源，例如：
  - `["/mock/bundle.json", "/mock/business-materials.json"]`
- 建议：基础/内置组件继续使用现有 `bundle.json`；业务组件与原子组件可放在同一 bundle，或单独使用 `business-materials.json`，便于与基础物料解耦、独立迭代。

### 4.5 插件环境（VSCode webview）下的 URL 处理

- 物料包 JSON 中的 `script` 通常为相对路径（如 `/mock/materials/mp-card.js`）。在**浏览器**中画布 iframe 的 base 与设计器一致，相对路径可解析；在 **VSCode 插件 webview** 中 iframe 的 base 为 `vscode-webview://...`，相对路径会被解析到错误协议导致 403。
- designer-demo 在插件环境下通过 **`src/composable/canvasDepsNormalizer.ts`** 订阅 `init_canvas_deps`，将相对路径转为「设计器前端绝对 URL」（如 `http://localhost:8090/mock/materials/mp-card.js`）后重新发布，画布拿到的即为可加载的绝对 URL；同时 `designerOrigin`、`useMaterial.getCanvasDeps`、`CanvasContainer` 在设计器侧发布依赖时也使用绝对 URL。因此**同一套物料配置**在浏览器与插件中均可使用，无需在物料 JSON 里写死绝对 URL。详见 `docs/VSCode-Integration.md` 中「固定 Mock 与物料包」「为什么导入的物料在插件中需要绝对 URL」等小节。

### 4.6 新增组件时的规则（保持简单）

- **新增原子组件**：在 mr 入口中增加对应 re-export；在物料中增加一条原子组件配置，`npm.script` 指向同一 mr 入口。
- **新增业务组件**：构建出对应 ESM 并部署；在物料中增加一条业务组件配置；构建时保持对 mr 入口的 external。
- **不引入**「业务组件自包含 + 设计器再单独供一份原子」的双重依赖，避免重复与复杂化。

### 4.7 导入组件的图标与国际化规则（必遵守）

所有导入设计器的业务组件与原子组件，需满足以下约定，以保证物料面板与画布展示一致、且支持中英文切换。

#### 4.7.1 图标

- **必须配备图标**：每条物料配置需提供 **`icon`** 字段（字符串，如 `"card"`、`"split"`），对应设计器内已注册的 SVG 图标名（小写）。
- **图标来源**：
  - 设计器内置图标：来自 `@opentiny/tiny-engine` 的 assets（如 `row`、`box`、`slot`、`table` 等），可直接作为 `icon` 使用。
  - 自定义图标：在 **designer-demo/src/assets/icons/** 下新增同名 `.svg` 文件（如 `card.svg`、`split.svg`），即可在物料中写 `"icon": "card"`；未配置 `icon` 或图标名不存在时，面板会使用默认图标 `component-default`。
- **新增组件时**：若希望专用图标，在物料 JSON 中写 `"icon": "xxx"`，并在 `src/assets/icons/` 下新增 `xxx.svg`；否则可不写 `icon`，将使用默认图标。

#### 4.7.2 分类与面板标题

- **分类约定**：原子组件（mr 开头）归为 **原子组件**，业务组件（mp 开头）归为 **业务组件**。物料 JSON 中 **`group`** 字段只填中文键：`"原子组件"` 或 `"业务组件"`。
- **面板显示**：设计器按当前语言自动映射为：
  - 中文：**原子组件** / **业务组件**
  - 英文：**MR Components** / **MP Components**
- 无需在物料中写英文分组名，由设计器统一做国际化。

#### 4.7.3 组件名称（物料面板与画布）

- **必须提供双语**：每条物料的 **`name`** 必须为对象，且包含 **`zh_CN`** 与 **`en_US`**，例如：
  ```json
  "name": { "zh_CN": "卡片", "en_US": "Card" }
  ```
- **面板与画布**：物料面板中的组件名称、以及拖拽到画布后的展示名称，均按设计器当前语言（中文/英文）自动切换；未提供 `en_US` 时英文环境下会回退到 `zh_CN`。
- **命名建议**：`en_US` 使用简短英文（如 Card、Divider、Progress），与组件语义一致，便于英文用户识别。

## 五、实施时注意事项（不写具体代码，仅要点）

1. **mr 入口与业务项目 resolver 一致**：命名、使用的 Vant/Ionic 子组件尽量与 mobilebanking 一致，避免行为差异。
2. **样式**：Vant、Ionic 的样式均需在设计器/预览中加载；可通过物料 `npm.css` 或预览入口统一引入。
3. **版本**：mr 入口所依赖的 Vant、Ionic 版本建议与业务项目一致或兼容。
4. **按需导出**：mr 入口可只导出设计器实际会用到的原子组件，减小体积。
5. **出码**：若出码逻辑会把 `npm.package`/version 写入生成项目的 package.json，对 `@local/xxx` 这类占位包需在出码侧单独处理（如不写入或写为本地 path），与「在设计器内使用」的可行性无关。

## 六、小结

| 项目         | 结论 |
|--------------|------|
| 业务组件导入 | 通过「源码构建 ESM + 物料配置」可行，无需发布 npm。 |
| 原子组件导入 | 需设计器提供实现；推荐「一个 mr 入口」同时接 Vant 与 Ionic。 |
| 推荐方案     | 设计器统一提供一份 mr 原子组件入口（+ Vant/Ionic 样式）；原子与业务组件均复用该入口。 |
| 流程         | 设计器提供 mr 入口与样式 → 原子组件作为物料录入（同 script、不同 exportName）→ 业务组件构建时 external 该入口并配置物料。 |
| 目标         | 简单、不繁琐；一套依赖、一套规则，便于持续接入新组件。 |

本文档可作为后续具体落地（构建脚本、物料 JSON 模板、import map 配置等）的指导依据，开发人员可据此理解目的、方案与流程，再分步实现。

## 七、新增业务组件实操步骤（以 mp-progress 为例）

以下为「从零把一个新业务组件接入设计器」的**详细展开**，与上文 [导入组件标准操作步骤](#导入组件标准操作步骤推荐) 一一对应，可按顺序执行。

### 7.1 把源码放到 materials-src

1. 在 **designer-demo/materials-src/** 下新建组件目录，例如 **mp-progress**。
2. 将业务组件源码放入该目录，至少包含：
   - **入口文件**：`index.js`，负责导出供设计器使用的组件名（与物料包里的 `component`、`exportName` 一致），例如：
     ```js
     import MpProgress from './mp-progress.vue';
     export { MpProgress };
     ```
   - **组件实现**：如 `mp-progress.vue`（若依赖原子组件，使用 `@local/mr-components` 等，与现有 mp-card 写法一致）。

目录结构示例：

```
materials-src/
  mp-card/           # 已有
    index.js
    mp-card.vue
  mp-progress/       # 新增
    index.js
    mp-progress.vue
  mr-components.js   # 原子组件入口（已有）
```

### 7.2 物料构建入口（已自动化，无需手改）

**build.lib.entry** 由 **scripts/get-material-entries.js** 在构建时**扫描 materials-src** 自动生成：

- 顶层 **.js 文件**（如 `mr-components.js`）→ entry 名为文件名去掉 `.js`。
- 顶层**子目录且存在 index.js**（如 `mp-card/index.js`）→ entry 名为目录名。

因此**新增业务组件时只需在 materials-src 下新建目录并放入 index.js 与 .vue**，无需再改 vite.materials.config.ts。执行 `pnpm run build:materials` 时会自动包含新目录。

### 7.3 在物料包 JSON 里登记组件

**推荐做法（清单 + 生成）**：在 **mock/materials-manifest.json** 的 `components` 中追加一条（字段见 [8.4](#84-物料清单-自动生成与校验推荐)），然后执行 **`pnpm run generate:materials-json`**，即可得到符合协议的 business-materials.json，无需手写下面字段。

**若需直接编辑 business-materials.json**，可按以下说明操作：
1. 打开 **designer-demo/mock/business-materials.json**。
2. 在 **data.materials.components** 中新增一条，重点包括：
   - **component**：画布使用的组件名，与入口导出名一致，如 `MpProgress`。
   - **npm**：`package` 用占位符如 `@local/mp-progress`，**script** 为 `/mock/materials/mp-progress.js`，**exportName** 为 `MpProgress`；若有单独样式则设 **css** 如 `/mock/materials/xxx.css`。
   - **icon**（必填）：设计器内已注册的图标名（小写），如 `"card"`、`"split"`；无专用图标时可省略，面板将使用默认图标。自定义图标需在 **designer-demo/src/assets/icons/** 下新增同名 `.svg`。
   - **name**（必填双语）：`{ "zh_CN": "进度条", "en_US": "Progress" }`，保证面板与画布在中文/英文切换时显示正确。
   - **group**：业务组件填 `"业务组件"`，原子组件填 `"原子组件"`；面板会按语言显示为「业务组件」/「原子组件」或「MP Components」/「MR Components」等（见 4.7 节）。
   - **schema**、**configure** 等按需填写（可先仿照 MpCard，再按组件能力调整）。
3. 在 **data.materials.snippets** 中，在对应 group（如「业务组件」）的 **children** 里增加一条 snippet，**snippetName** 与 **component** 一致（如 `MpProgress`），**name**、**icon** 与上一步一致，便于在物料面板中拖拽。

### 7.4 执行构建

在 **designer-demo** 目录下执行：

```bash
pnpm run build:materials
```

产物会直接写入 **public/mock/materials/**（如 `mp-progress.js`）。无需再复制或改 package.json。

**重要**：`public/mock/materials/` 下的内容**全部由构建自动生成**，不要直接编辑该目录。只需维护 **materials-src/** 下的源码，改完后执行一次 `pnpm run build:materials` 即可更新。

### 7.5 验证

1. 运行设计器：`pnpm run dev`，浏览器打开 `http://localhost:8090`。
2. 在物料面板中找到新组件（如「进度条」），拖入画布，能正常渲染即表示接入成功。
3. 若在 VSCode 插件环境中使用，同样应能拖拽与渲染（设计器会自动做相对路径 → 绝对 URL 的转换）。

---

**小结**：新增一个业务组件 = **① 源码放入 materials-src/组件名**（含 index.js）→ **② materials-manifest.json 增加一条并执行 generate:materials-json**（或直接编辑 business-materials.json）→ **③ 执行 build:materials**（自动扫描 materials-src，无需改 vite 配置）→ **④ 验证**。推荐始终使用清单 + 生成，避免手写协议字段。

## 八、常见问题

### 8.1 public/mock/materials 下的文件是自动生成的吗？

**是。** 该目录由 **`pnpm run build:materials`**（即 `vite build --config vite.materials.config.ts`）生成，产物包括：

- **mr-components.js**、**mp-card.js**、**mp-progress.js** 等：对应 materials-src 里配置的每个 entry。
- **style.css**：各 Vue 组件中引用的样式打包结果。
- **_plugin-vue_export-helper-xxxxx.js**：**Vite 的 @vitejs/plugin-vue** 在编译 Vue 单文件组件时生成的运行时辅助函数（用于 `<script setup>` 的 export 等），由构建自动产出，**无需也请不要手动修改**。哈希后缀用于缓存与区分版本。

你只需要维护 **materials-src/** 下的源码，改完后执行一次 `pnpm run build:materials`，即可刷新 `public/mock/materials/` 下的内容。

### 8.2 business-materials.json 怎么改？手动添加一个组件要从哪下手？

该文件是**设计器物料注册表**，需要**手动编辑**（或通过脚本批量生成）。结构可以概括为：

- **data.materials.components**：数组，每个元素 = 一个在画布里可用的组件。必填核心字段：
  - **component**：画布组件名（如 `MpProgress`），与 materials-src 里导出的名字一致。
  - **npm**：`package`（占位如 `@local/mp-progress`）、**script**（如 `/mock/materials/mp-progress.js`）、**exportName**（同上）、**css**（若有）。
  - **name**：`{ "zh_CN": "进度条", "en_US": "Progress" }`。
  - **group**：`"原子组件"` 或 `"业务组件"`。
  - **icon**：图标名（小写），对应 `src/assets/icons/xxx.svg` 或内置图标。
  - **schema**：属性面板分组与表单项（properties[].label 建议含 zh_CN、en_US）。
  - **configure**：画布行为（是否容器、右键菜单等），可复制现有组件的配置。
- **data.materials.snippets**：数组，每个元素 = 物料面板里的一个**分组**（如「业务组件」）。每个分组的 **children** 里列出该分组下要展示的组件：
  - **snippetName**：与 components 里的 **component** 一致（如 `MpProgress`）。
  - **name**、**icon**：与 components 里一致，用于面板展示。

**手动添加一个组件的步骤**：在 **components** 数组末尾加一条（可复制 MpCard 或 MpProgress 那条，改 component、npm、name、icon、schema 等），再在 **snippets** 里找到对应 **group** 的 **children**，加一条同名的 snippet（snippetName、name、icon 与 components 一致）。

### 8.3 要大量添加组件时怎么做？

- **方式一（推荐）**：使用 **物料清单 + 自动生成**（见 [8.4](#84-物料清单自动生成与校验推荐)），只维护 `mock/materials-manifest.json`，运行 `pnpm run generate:materials-json` 即可得到符合协议的 business-materials.json，无需手写协议字段。
- **方式二**：按 8.2 的规则，手写或自写脚本根据「组件名单」生成 components 和 snippets 的条目，再合并进 business-materials.json。
- **方式三**：在 business-materials.json 里为每个组件复制一条现有组件，用编辑器的多光标或查找替换批量改字段，再在 snippets 里批量补上对应的 children。
- **注意**：大量添加前，每个组件仍需在 **materials-src** 下有对应目录（含 index.js）或顶层 .js 文件；**无需**改 vite.materials.config.ts（构建时会自动扫描）。然后执行 **build:materials**，否则画布会加载不到脚本。

### 8.4 物料清单 + 自动生成与校验（推荐）

为避免手写 protocol 时字段繁多、易出错，designer-demo 提供**清单驱动**的生成与校验：

1. **维护清单**：编辑 **mock/materials-manifest.json**，在 `components` 数组中为每个组件填**少量必填字段**即可：**component**、**group**、**nameZh** / **nameEn**、**icon**、**script**、**exportName**、**package**、**hasCss**；可选 **description**、**isContainer**、**schemaExtra**（覆盖默认 schema）、**shortcuts**。
2. **生成**：执行 `pnpm run generate:materials-json`，脚本按 TinyEngine 协议补全 configure、schema、snippets 等，写入 **mock/business-materials.json**。
3. **校验**：执行 `pnpm run validate:materials-json`，检查必填字段，不符合时报错，便于 CI 或本地自查。

**新增组件时**：在 manifest 的 `components` 中追加一条（可复制现有条再改），需自定义属性面板时配置 **schemaExtra**，再运行 `generate:materials-json` 即可。
