## 业务与原子组件导入设计器方案（旧流程说明）

> **本文仅描述早期在设计器仓库内本地构建物料的方案，用于历史回溯与问题排查。  
> 当前推荐方案是「主工程产出物料包 + 设计器加载」，详见 `业务与原子组件导入方案.md` 以及各主工程仓库的 `lowcode-materials/README.md`、`DESIGN_TIME_COMPAT.md`。**

---

### 1. 旧流程的核心思路（materials-src 本地构建）

- **源码位置**：在 `designer-demo/materials-src/**` 下维护所有要给设计器用的业务组件（`mp-*`）与原子组件入口（`mr-components.js`）。
- **构建命令**：通过 `pnpm run build:materials`（内部曾使用 `vite.materials.config.ts`，该文件已删除），把 `materials-src/**` 编译为 ESM，产出到 `public/mock/materials/` 目录。
- **物料描述**：
  - 维护 `mock/materials-manifest.json`，描述组件的基本信息（component、group、nameZh/nameEn、icon、script、exportName、package、hasCss 等）。
  - 执行 `pnpm run generate:materials-json` 生成 `mock/business-materials.json`，由设计器按 TinyEngine 物料协议加载。
- **设计器加载方式**：
  - `engine.config.material = ["/mock/bundle.json", "/mock/business-materials.json"]`。
  - 设计器通过 `/mock/bundle.json` 与 `/mock/business-materials.json` 合并出最终物料列表，在浏览器或 VSCode webview 中渲染。

这一套流程的特点是：**所有物料都在 designer-demo 仓库内维护和构建**，主工程只作为源码参考，不直接对接物料产出。

---

### 2. 旧流程下业务组件 / 原子组件的导入步骤（概要）

#### 2.1 业务组件（mp-xxx）

1. 在 `materials-src/` 下按组件名新建目录（例如 `mp-card/`、`mp-progress/`），放入：
   - `index.js`：导出供画布使用的组件（例如 `export { MpCard } from './mp-card.vue'`）。
   - 组件实现 `.vue` 文件。
2. 在 `mock/materials-manifest.json` 的 `components` 数组中追加一条，配置：
   - `component`、`group`（"业务组件"）、`nameZh` / `nameEn`、`icon`。
   - `script`（如 `mp-card.js`）、`exportName`、`package`（如 `@local/mp-card`）、`hasCss`。
   - 可选 `description`、`schemaExtra` 等。
3. 执行：
   - `pnpm run generate:materials-json` → 生成 `business-materials.json`。
   - `pnpm run build:materials` → 生成 `/mock/materials/mp-card.js` 等产物。
4. 在浏览器或 VSCode 插件中运行设计器，拖拽验证组件效果。

#### 2.2 原子组件（mr-xxx）

1. 在 `materials-src/mr-components.js` 中，从 Vant / Ionic 引入组件并以 `Mr*` 命名导出，例如：
   - `export { Divider as MrDivider } from 'vant';`
2. 在 `mock/materials-manifest.json` 的 `components` 中为每个原子组件追加一条记录：
   - `component`（如 `MrDivider`）、`group`（"原子组件"）、`nameZh`/`nameEn`、`icon`。
   - `script` 固定为 `mr-components.js`，`package` 为 `@local/mr-components`，`exportName` 对应具体导出名。
3. 按业务组件相同步骤生成 `business-materials.json` 并执行 `build:materials`。

### 3. 旧流程的局限性与问题

- **与主工程强耦合但分仓维护**：
  - 业务组件源码从主工程「复制」到 `materials-src`，需要人工保持同步，容易出现版本漂移。
  - 一旦主工程改动接口 / 样式，设计器侧需要手工跟进。
- **构建链路重复**：
  - 设计器仓库曾维护自己的 Vite 配置、脚本（`get-material-entries.js` 等已删除）以及大量 mock 物料产物。
  - 主工程自身往往也有 Vite / 打包逻辑，重复维护成本高。
- **复杂组件要在设计器里再造一遍运行时**：
  - 为了在画布里运行，复杂业务组件需要额外引入 `src/runtime` 里的 store / router / i18n 桩，且这些桩只存在于 designer-demo。
  - 一旦主工程真实运行时更新，设计器的桩也要手动跟进。

这些问题在组件数量增加、业务复杂度提升后会变成维护负担，因此在完成「可行性验证」之后，方案逐步演进到了**由主工程统一产出物料包**。

---

### 4. 与当前推荐方案的关系

当前我们采用的方案是：

- **物料入口与设计时兼容组件放在主工程仓库**（例如 `mobilebanking/lowcode-materials/**`）；
- **主工程执行 `build:designer-materials`**，统一：
  - 提取设计 token / 基础样式；
  - 构建设计时兼容版组件（`mp-input-designer.vue`、`mp-account-input-canvas.vue` 等）；
  - 生成符合物料协议的 `bundle.json` 与组件 ESM/CSS；
- **设计器与 VSCode 插件仅负责加载这些 bundle**（通过 `engine.config.material`、`window.TINY_MATERIAL_BUNDLE_URLS` 等）。

> 旧流程（materials-src 本地构建）在设计阶段帮助我们验证了「主工程源码 → 物料协议 → 设计器画布」的整体可行性；在确认方案可行且主工程已经具备稳定的 `lowcode-materials` 目录后，这套流程已不再推荐用于新增组件接入，仅保留此文档作为历史记录与排查参考。
